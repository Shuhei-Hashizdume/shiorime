## 1. データベース

### 削除時の連動

- 本・気づき・AI提案は `user_id` を持ち、アカウント削除時はまとめて削除する（`ON DELETE CASCADE`）。
- 気づきの `book_id` は、本の削除時に NULL にする（`ON DELETE SET NULL`）。
- AI提案（`ai_proposals`）は、気づきの削除時にまとめて削除する（`ON DELETE CASCADE`）。
- 個人のAI利用回数（`ai_usages`）も、アカウント削除時にまとめて削除する（`ON DELETE CASCADE`）。アプリ全体の利用回数は削除しない。

### 気づき

- 気づきは、作成時に `book_title`・`book_author`・`book_cover_url` と、元の本の識別番号（`original_book_id`）をコピーして保存する。
- `original_book_id` は本を削除しても消さない。
- 本が存在する間は、本のタイトル・著者の編集時にコピーも同時更新する。
- 削除済みの本の気づきは `original_book_id` でまとめる。
- 公開範囲（`visibility`）は MVP では API で受け付けず、サーバー側で常に `private` にする。

### AI提案

- AI提案は、開始時点の気づきの本文・引用のコピーを保存する。行動プランの作成時はこのコピーをAIに渡す。
- AI提案の状態：深掘りの作成中 → 回答待ち → 行動プランの作成中 → 完了（要件定義書の表記に合わせる）。
  - 行動プランの作成中に利用者が画面を離れても、処理は続け、完了すれば保存する。
  - 完了以外のAI提案は、気づきの詳細に表示するAI提案・次の一歩の数（気づきの削除時の確認を含む）には含めない。
- 完了していないAI提案の後片付け：
  - 同じ気づきで新しいAI提案を始めたときに、回答待ちのものを削除する。
  - 回答待ちのまま24時間たったものは定期的に削除する。
  - AI提案画面を開いたとき、そのAI提案が深掘りの作成中・回答待ちであれば、画面からサーバーへ明示的に終了を伝え、そのAI提案を削除する（状態を変える操作なので GET では作らない。具体的な API は設計書で扱う）。回数は戻らない。深掘りの作成中に削除した場合、AI が後から深掘りを作り終えても保存しない（「4. AI 連携」の、処理中に AI提案が削除された場合のとおり）。
  - 利用者が画面を離れた瞬間をサーバーは確実には検知できないため、利用者から見て「離れたら消える」動きは、画面を開き直したときに新しいAI提案を始めず「終了しました」と表示して上記の終了処理を行うことと、この後片付けで実現する。画面を離れたことを検知して削除APIを呼ぶ処理は作らない。
- AI提案には、回数を数えた日付（日本時間）を記録する（止まったとみなして回数を戻すときに、+1 した日付の行を特定するため）。
- 状態を変えた日時を記録し、深掘りの作成中・行動プランの作成中のまま2分経過したものを「止まった」と判定できるようにする。

### 本

- 本は Google Books のボリューム ID を保存する（手入力の本は NULL）。
- 同じユーザーで同じボリューム ID の本は登録できない（NULL は重複を許す）。
- ISBN は任意で保存する。ある場合は13桁の形式にそろえる（第3段階で「同じ本を読んだ人」を探すため）。
- 読書ステータス：`reading` / `finished`。読了日は持たない。
- 表紙のURLがない本（手入力の本、Google Books に表紙がない本）は、`cover_image_url` を NULL とし、画面では用意したアイコン画像を表示する。気づきの `book_cover_url` も同様。

### ユーザー

- メールアドレスは小文字にそろえて保存し、一意にする。
- ユーザーは「メールアドレス確認済みかどうか」の項目を持つ（MVPでは常に未確認）。第2段階で本人確認を入れる際のデータ移行を楽にするため。
- ユーザーはトークンのバージョン番号を持ち、パスワード変更時に番号を上げる。JWTに番号を含め、古い番号のJWTは拒否する。

### AIの利用回数

- AIの利用回数は専用テーブル `ai_usages`（`user_id`、日付（日本時間）、回数）で管理する。
  - `user_id` と日付の組み合わせは一意。
  - AI提案のデータの件数では数えない（AI提案が削除されても回数が戻らないようにするため）。
- アプリ全体の1日の利用回数は、`user_id` を持たない別のテーブルで管理する（退会しても減らないようにするため）。

### 共通

- 日時はすべてUTCで保存し、「今日」の判定時だけ日本時間に変換する。
- DB の構造変更は Alembic で管理する。

## 2. 競合（連打・同時実行）対策

### AI提案の開始時

- 同じ気づきで「深掘りの作成中」または「行動プランの作成中」のAI提案があれば開始しない。
- なければ、回答待ちのAI提案を削除し、「深掘りの作成中」のAI提案を作成する。
- この確認と作成は DB で原子的に行う（同時に2つ来ても1つしか作られない）。

### 回数の確保

- 「回数が5未満なら+1」を DB への1回の命令で行う（例：`UPDATE ... SET count = count + 1 WHERE ... AND count < 5 RETURNING count`）。
- 個人とアプリ全体の +1 は1つのトランザクションで行い、どちらかが上限に達していれば両方とも消費しない。
- 深掘りの作成に失敗したら、個人とアプリ全体の両方を -1 する（-1 は +1 したのと同じ日付の行に対して行う）。
- 深掘りの作成に失敗したときの -1 は、そのAI提案が「深掘りの作成中」のまま残っている場合だけ行う。「残っていれば削除して -1 する」を DB への1回の命令で行い、すでに削除されていれば（開き直しによる終了など）何もしない。
- 深掘りの作成に成功したときも同様に、そのAI提案が残っている場合だけ「回答待ち」にして保存する。
- 理由：開き直しで終了させた後にAIが失敗した場合に、回数を戻してしまわないようにするため。
- テストに「深掘りの作成中に終了させた後、AIが失敗しても回数が戻らない」を含める。

### 回答の送信時

- AI提案の状態を「回答待ち → 行動プランの作成中」に DB への1回の命令で変え、変更できた処理だけが AI を呼ぶ。
- 成功したら「完了」、失敗したら「回答待ち」に戻す。
- 「完了」にする処理と、同じ気づきの前の完了したAI提案を削除する処理は、1つのトランザクションで行う（要件定義書 5.5「保存するAI提案の数」）。
- データベースでも、1つの気づきに完了したAI提案は1件までとする制約を付ける（例：状態が完了の行に限った部分ユニーク索引）。
- 成功時の保存・失敗時の「回答待ち」への戻しは、どちらもそのAI提案が「行動プランの作成中」のまま残っている場合だけ行う（確認と変更を DB への1回の命令で行う）。すでに削除されていれば何もしない。
  - 理由：処理中に削除されたAI提案が、保存されたり「回答待ち」として復活したりしないようにするため。
- 回答を送った後に利用者が画面を離れ、行動プランの作成に失敗した場合、そのAI提案は「回答待ち」に戻り、利用者からは見えないまま24時間の後片付けで削除される（要件定義書「既知の制限」のとおり）。

### テスト

- テストに次を含める。
  - 残り1回の状態で同時に2つ送ると、成功は1つだけ
  - 同じ気づきで同時に2つ開始しても、AI提案は1つだけ作られる

## 3. 認証

- パスワードのハッシュ化：Argon2id（例：pwdlib）。
  - 理由：bcrypt の72バイト制限（日本語では約24文字を超えた部分が無視される）を避けるため。
- パスワードの前後の空白の除去は、Pydantic の空白除去の設定（`str_strip_whitespace` など）を使い、登録・ログイン・パスワード変更・退会のすべての入口で適用する。
- JWT を発行し、httpOnly・Secure・SameSite=Lax の Cookie で渡す。MVP はアクセストークンのみ・有効期限7日（JWT の exp）。Cookie の期限は30日にして、期限切れを見分けられるようにする（api.md 3-3）。リフレッシュトークンは第2段階。
- ログアウト時は、発行時と同じ属性で Cookie を削除する。
- 有効期限内のJWTでも、ユーザーが存在しない（退会済み）場合は拒否する。
- CSRF 対策：SameSite=Lax と、状態を変える操作を GET で作らないこと。必要なら Origin ヘッダーの確認も加える（設計時に決める）。
- CORS の扱い：画面と API を同じドメインから配信するため、本番では不要になる可能性が高い。設計時に再検討する。
- ログイン試行・新規登録の回数制限は、接続元の IP アドレス単位で行う。Caddy の後ろでは、Caddy から渡される接続元の情報（`X-Forwarded-For`）だけを信頼する設定にする（しないと、全利用者が同じ接続元に見えて、まとめて制限される）。

## 4. AI 連携

- 1回の呼び出しのタイムアウトは30秒、自動リトライは1回。
- 出力形式は固定する（例：JSON で深掘りと行動プランを分ける）。サーバー側でも形式を検証し、不正ならリトライ対象の失敗として扱う。
- 気づきが長い場合も論点がぼやけないよう、プロンプトで「最も重要な点に絞って深掘りを作る」と指示する。
- AIの出力は、画面では常にプレーンテキストとして表示する（HTMLとして扱わない）。
- AIの処理中に、そのAI提案自体が削除された場合（気づきの削除、退会、新しいAI提案の開始、24時間の後片付け、AI提案画面の開き直しによる終了など）は、結果を保存せずに終了する。
- テストでは OpenAI API をモックに置き換える。

## 5. インフラ

- Docker Compose で Caddy ＋ FastAPI ＋ PostgreSQL の3コンテナ構成。ローカルでも本番と同じ構成で開発し、完成後に EC2 へデプロイする。
- Caddy をリバースプロキシにし、画面とAPIを同じドメインから配信する（例：`/` は画面、`/api` は FastAPI）。
- 独自ドメインを取得し、Caddy の自動 HTTPS を使う。
- PostgreSQL のポートは外部に公開しない。
- AWS の請求アラートを設定する。

## 6. テスト

- pytest で API テスト。正常系・異常系（境界値を含む）。
- 境界値の例：

| 対象         | 境界値                                 |
| ------------ | -------------------------------------- |
| パスワード   | 7文字NG・8文字OK・128文字OK・129文字NG |
| 気づきの本文 | 1000文字OK・1001文字NG                 |
| AI提案       | 5回目OK・6回目NG                       |
| ログイン試行 | 5回目OK・6回目NG                       |

- 日次リセットのテストは、現在時刻を差し替えて行う（例：freezegun）。
- テスト用の DB は、本番と同じ PostgreSQL を使う。
- GitHub Actions で push のたびに自動実行する。
- 競合対策のテストは「[2. 競合（連打・同時実行）対策](#2-競合連打同時実行対策)」を参照。

## 7. 画面のワイヤーフレーム（暫定版）

**この節は古い。画面は design/screens.md で置き換え済みで、食い違う場合は screens.md を正とする。**

### 共通

- 編集・削除は、ボタンを並べず、タイトル右上の「⋮」メニューから操作する形にする（アプリ全体で統一する）。

### 本の詳細

- 表紙・タイトル・著者
- タイトル右上の「⋮」（編集はその場の入力窓、削除は確認表示）
- 読書ステータスの選択（選ぶとすぐ保存）
- この本の気づきの件数
- 「＋気づきを書く」「この本の気づきを見る →」
- 画面下部に共通メニュー（本棚・気づき一覧・プロフィール）

### 気づきの詳細

- 本・ページ・引用・本文
- 右上の「⋮」（編集・削除）
- 「AI提案を受ける」ボタン
- 「AI提案：本日あと◯回（気づきの登録は何件でもできます）」
- 次の一歩（最新の完了したAI提案だけ。1つの気づきに1つ。詳細は screens.md「6. 気づきの詳細」）

### AI提案

1. 深掘りの作成中：「あなたの気づき」を表示し、「AIが質問を考えています…（最大1分ほどかかります）」
2. 深掘りの表示：「AIからの深掘り」、回答の入力欄（◯/500字）、外部AIへの送信の注意書き、「回答して行動プランを受け取る」ボタン
3. 行動プランの作成中：深掘りと回答を表示し、「AIが行動プランを考えています…（最大1分ほどかかります）」
4. 行動プランの表示：行動プラン1〜3個、「気づきに戻る」ボタン（自動で保存済み）

- 3で失敗した場合：エラー文と「もう一度送る（回数は使いません）」ボタン
- 回答を送る前に戻ろうとした場合：要件定義書の確認文を表示（行動プランの作成中は表示しない）
- 深掘りの作成中・回答待ちのAI提案を開き直した場合：「このAI提案は終了しました」と、気づきの詳細画面に戻るボタン

## 8. 設計工程で決めること

### 構成・運用

- フロントエンドの構成（React＋Vite でビルドして Caddy で配信するか）と、開発時の構成（Secure Cookie を含む）
- ログに出してよい情報・出してはいけない情報、.env の管理
- DB のバックアップ方法

### API

- API のエラーレスポンスの形式とステータスコード
- AI提案画面の URL の形式（AI提案ごとに分ける）

### AI 連携・利用制限

- AI 出力のスキーマ、最大出力量、リトライする失敗の分類
- 行動プランの作成に失敗した場合の再送信の回数に上限を設けるか（失敗した呼び出しにも料金が発生する場合があるため）
- 行動プランの作成に失敗した後、「もう一度送る」の前に回答を書き直せるか
- 行動プランの保存形式
- AIサービス側の月の利用上限額の設定方法（最新の管理画面で、確実に止まる上限として設定できるかを確認する）
- 「2分経過で止まったとみなす」判定と「24時間の後片付け」を、いつ・どの処理で行うか（開始時や回数表示時にその場で判定するか、定期処理にするか）。定期処理にする場合、Docker Compose のどこで動かすか。止まったと判定されるまでの間の表示
- アプリ全体の上限に達しているときの「本日の残り回数」の表示 → 決定済み（screens.md「6. 気づきの詳細」）

### 入力・表示

- 文字数の数え方（画面とサーバーで一致させる方法）
- 並び順：本棚、本ごとの気づき一覧、AI提案の履歴 → 決定済み（screens.md。AI提案は1つの気づきに1つだけのため並び順は不要）

### Google Books

- Google Books の扱い：上限を超える長さのタイトル・著者の扱い、APIキーの要否、利用規約上の表示の要否
  - 決定済み（screens.md「2. 本の検索・登録」）：検索はサーバー経由、表紙URLはサーバーで https に直す、検索の回数制限は1人1分10回、出版年は検索結果に表示するだけで保存しない
- Google Books API の利用枠と、枠を超えたときの表示

### 認証・不正利用の防止

- 新規登録の回数制限に達したときの表示文 → 決定済み（screens.md「10. 新規登録・ログイン」）
- ログイン試行・新規登録の回数制限で、何を数えるか（失敗だけか、成功も含むか。新規登録は、登録済みエラーを含む試行を数えることを推奨）
- パスワード変更・退会時のパスワード再入力に、回数制限を設けるか

### 画面遷移

- ログイン画面と新規登録画面の相互の移動、ログイン中にログイン画面を開いた場合の扱い
- ログイン後に利用規約・プライバシーポリシーを見られる場所
- 気づきの編集中にログインの期限が切れた場合の扱い

### 規約・プライバシー

- 利用規約への同意日時を記録するか
- プライバシーポリシーの記載事項（運営者の連絡先、外国にある第三者への提供の扱い、OpenAI 側でのデータ保持期間など。最新の法令・規約を確認する）
