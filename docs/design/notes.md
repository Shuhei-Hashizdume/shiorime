## 1. データベース

### 削除時の連動

- 本・気づき・AI提案は `user_id` を持ち、アカウント削除時はまとめて削除する（`ON DELETE CASCADE`）。
- 気づきの `book_id` は、本の削除時に NULL にする（`ON DELETE SET NULL`）。
- AI提案（`ai_proposals`）は、気づきの削除時にまとめて削除する（`ON DELETE CASCADE`）。
- 個人のAI利用回数（`ai_usages`）も、アカウント削除時にまとめて削除する（`ON DELETE CASCADE`）。アプリ全体の利用回数は削除しない。

### 気づき

- 気づきは、作成時に `book_title`・`book_author`・`book_cover_url` と、元の本の識別番号（`original_book_id`）をコピーして保存する。
- `original_book_id` は本を削除しても消さない。
- 本が存在する間は、本のタイトル・著者の編集時にコピーも同時更新する。
- 削除済みの本の気づきは `original_book_id` でまとめる。
- 気づきには公開範囲（`visibility`）を持たせない。気づきは本人だけが見るもので、第3段階で公開するのは読了投稿（別の表）のため（要件定義書「公開範囲」、2026-10-25 変更）。

### AI提案

- AI提案は、開始時点の気づきの本文・引用のコピーを保存する。行動プランの作成時はこのコピーをAIに渡す。
- AI提案の状態：深掘りの作成中 → 回答待ち → 行動プランの作成中 → 完了（要件定義書の表記に合わせる）。このほかに、失敗して終わった状態を2つ持つ：深掘りの作成に失敗（`question_failed`）、送り直しの上限に達した（`retry_limit_reached`）。どちらも失敗した瞬間に回数を戻し、行はすぐには消さず24時間の後片付けで消す（画面が問い合わせで失敗の理由を知れるようにするため。api.md 7-6）。
  - 行動プランの作成中に利用者が画面を離れても、処理は続け、完了すれば保存する。
  - 完了以外のAI提案は、気づきの詳細に表示するAI提案・次の一歩の数（気づきの削除時の確認を含む）には含めない。
- 完了していないAI提案の後片付け：
  - 同じ気づきで新しいAI提案を始めたときに、回答待ちのものを削除する。
  - 回答待ちのまま24時間たったものは定期的に削除する。
  - AI提案画面を開いたとき、そのAI提案が深掘りの作成中・回答待ちであれば、画面からサーバーへ明示的に終了を伝え、そのAI提案を削除する（状態を変える操作なので GET では作らない。具体的な API は設計書で扱う）。回数は戻らない。深掘りの作成中に削除した場合、AI が後から深掘りを作り終えても保存しない（「4. AI 連携」の、処理中に AI提案が削除された場合のとおり）。
  - 利用者が画面を離れた瞬間をサーバーは確実には検知できないため、利用者から見て「離れたら消える」動きは、画面を開き直したときに新しいAI提案を始めず「終了しました」と表示して上記の終了処理を行うことと、この後片付けで実現する。画面を離れたことを検知して削除APIを呼ぶ処理は作らない。
- AI提案には、回数を数えた日付（日本時間）を記録する（止まったとみなして回数を戻すときに、+1 した日付の行を特定するため）。
- 状態を変えた日時を記録し、深掘りの作成中・行動プランの作成中のまま2分経過したものを「止まった」と判定できるようにする。

### 本

- 本は Google Books のボリューム ID を保存する（手入力の本は NULL）。
- 同じユーザーで同じボリューム ID の本は登録できない（NULL は重複を許す）。
- ISBN は任意で保存する。Google Books に13桁の ISBN があるときだけ保存し、10桁しかない場合は保存しない（第3段階で「同じ本を読んだ人」を探すため。api.md 7-3、2026-10-27）。
- 読書ステータス：`reading` / `finished`。読了日は持たない。
- 表紙のURLがない本（手入力の本、Google Books に表紙がない本）は、`cover_url` を NULL とし、画面では用意したアイコン画像を表示する。気づきの `book_cover_url` も同様。

### ユーザー

- メールアドレスは小文字にそろえて保存し、一意にする。
- ユーザーは「メールアドレス確認済みかどうか」の項目を持つ（MVPでは常に未確認）。第2段階で本人確認を入れる際のデータ移行を楽にするため。
- ユーザーはトークンのバージョン番号を持ち、パスワード変更時に番号を上げる。JWTに番号を含め、古い番号のJWTは拒否する。

### AIの利用回数

- AIの利用回数は専用テーブル `ai_usages`（`user_id`、日付（日本時間）、回数）で管理する。
  - `user_id` と日付の組み合わせは一意。
  - AI提案のデータの件数では数えない（AI提案が削除されても回数が戻らないようにするため）。
- アプリ全体の1日の利用回数は、`user_id` を持たない別のテーブルで管理する（退会しても減らないようにするため）。

### 共通

- 日時はすべてUTCで保存し、「今日」の判定時だけ日本時間に変換する。
- DB の構造変更は Alembic で管理する。

## 2. 競合（連打・同時実行）対策

### AI提案の開始時

- 同じ気づきで「深掘りの作成中」または「行動プランの作成中」のAI提案があれば開始しない。
- なければ、回答待ちのAI提案と、失敗して終わったAI提案（`question_failed`・`retry_limit_reached`）を削除し、「深掘りの作成中」のAI提案を作成する（api.md 7-6）。
- この確認と作成は DB で原子的に行う（同時に2つ来ても1つしか作られない）。

### 回数の確保

- 「回数が5未満なら+1」を DB への1回の命令で行う（例：`UPDATE ... SET count = count + 1 WHERE ... AND count < 5 RETURNING count`）。
- 個人とアプリ全体の +1 は1つのトランザクションで行い、どちらかが上限に達していれば両方とも消費しない。
- 深掘りの作成に失敗したら、個人とアプリ全体の両方を -1 する（-1 は +1 したのと同じ日付の行に対して行う）。
- 深掘りの作成に失敗したときの -1 は、そのAI提案が「深掘りの作成中」のまま残っている場合だけ行う。「まだ深掘りの作成中なら `question_failed`（深掘りの作成に失敗して終わった）にして -1 する」を DB への1回の命令で行い、すでに削除されていれば（開き直しによる終了など）何もしない。行はすぐには消さず、24時間の後片付けで消す（api.md 7-6）。
- 深掘りの作成に成功したときも同様に、そのAI提案が残っている場合だけ「回答待ち」にして保存する。
- 理由：開き直しで終了させた後にAIが失敗した場合に、回数を戻してしまわないようにするため。
- テストに「深掘りの作成中に終了させた後、AIが失敗しても回数が戻らない」を含める。

### 回答の送信時

- AI提案の状態を「回答待ち → 行動プランの作成中」に DB への1回の命令で変え、変更できた処理だけが AI を呼ぶ。
- 成功したら「完了」、失敗したら「回答待ち」に戻す（画面では送り直し待ち `plan_failed`）。最初の送信と送り直し3回の、4回目の失敗では `retry_limit_reached` にし、本人の回数を1回戻す（api.md 2-5）。4回目の送信の途中で止まった（2分たった）場合も同じ（api.md 2-8）。
- 「完了」にする処理と、同じ気づきの前の完了したAI提案を削除する処理は、1つのトランザクションで行う（要件定義書 5.5「保存するAI提案の数」）。
- データベースでも、1つの気づきに完了したAI提案は1件までとする制約を付ける（例：状態が完了の行に限った部分ユニーク索引）。
- 成功時の保存・失敗時の「回答待ち」への戻しは、どちらもそのAI提案が「行動プランの作成中」のまま残っている場合だけ行う（確認と変更を DB への1回の命令で行う）。すでに削除されていれば何もしない。
  - 理由：処理中に削除されたAI提案が、保存されたり「回答待ち」として復活したりしないようにするため。
- 回答を送った後に利用者が画面を離れ、行動プランの作成に失敗した場合、そのAI提案は「回答待ち」に戻り、気づきの詳細に「次の一歩を作成できませんでした」と知らせる（api.md 2-3）。新しいAI提案を始めるか、24時間の後片付けで削除される。

### テスト

- テストに次を含める。
  - 残り1回の状態で同時に2つ送ると、成功は1つだけ
  - 同じ気づきで同時に2つ開始しても、AI提案は1つだけ作られる

## 3. 認証

- パスワードのハッシュ化：Argon2id（例：pwdlib）。
  - 理由：bcrypt の72バイト制限（日本語では約24文字を超えた部分が無視される）を避けるため。
- パスワードの前後の空白の除去は、Pydantic の空白除去の設定（`str_strip_whitespace` など）を使い、登録・ログイン・パスワード変更・退会のすべての入口で適用する。
- JWT を発行し、httpOnly・Secure・SameSite=Lax の Cookie で渡す。MVP はアクセストークンのみ・有効期限7日（JWT の exp）。Cookie の期限は30日にして、期限切れを見分けられるようにする（api.md 3-3）。リフレッシュトークンは第2段階。
- ログアウト時は、発行時と同じ属性で Cookie を削除する。
- 有効期限内のJWTでも、ユーザーが存在しない（退会済み）場合は拒否する。
- CSRF 対策：SameSite=Lax と、状態を変える操作を GET で作らないこと。必要なら Origin ヘッダーの確認も加える（設計時に決める）。
- CORS の扱い：画面と API を同じドメインから配信するため、本番では不要になる可能性が高い。設計時に再検討する。
- ログイン試行・新規登録の回数制限は、接続元の IP アドレス単位で行う。Caddy の後ろでは、Caddy から渡される接続元の情報（`X-Forwarded-For`）だけを信頼する設定にする（しないと、全利用者が同じ接続元に見えて、まとめて制限される）。

## 4. AI 連携

- 1回の呼び出しのタイムアウトは30秒、自動リトライは1回。
- 出力形式は固定する（例：JSON で深掘りと行動プランを分ける）。サーバー側でも形式を検証し、不正ならリトライ対象の失敗として扱う。
- 気づきが長い場合も論点がぼやけないよう、プロンプトで「最も重要な点に絞って深掘りを作る」と指示する。
- AIの出力は、画面では常にプレーンテキストとして表示する（HTMLとして扱わない）。
- AIの処理中に、そのAI提案自体が削除された場合（気づきの削除、退会、新しいAI提案の開始、24時間の後片付け、AI提案画面の開き直しによる終了など）は、結果を保存せずに終了する。
- テストでは OpenAI API をモックに置き換える。

## 5. インフラ

- Docker Compose で Caddy ＋ FastAPI ＋ 片付け（worker）＋ PostgreSQL の4コンテナ構成（片付けのコンテナは api.md 2-8 で追加）。ローカルでも本番と同じ構成で開発し、完成後に EC2 へデプロイする。
- 起動のときだけ動く使い切りのコンテナ `migrate` を足す。api と同じイメージで `alembic upgrade head` を動かし、終わったら止まる。常に動くのは4つのコンテナのまま。
  - 起動の順番：db の準備ができる（ヘルスチェック）→ migrate がマイグレーションを当てる → 成功したら api と worker が起動する。失敗したら api と worker は起動しない。
  - 理由：テーブルの形を変えるのを migrate の1か所だけにするため。api の起動に入れると、同じイメージの worker も動かして同時に当てようとしたり、開発中に api の命令を `--reload` に差し替えたときに書き忘れたりするため。FastAPI を2つ以上に増やしても、当てるのは1回だけで済む。
- Caddy をリバースプロキシにし、画面とAPIを同じドメインから配信する（例：`/` は画面、`/api` は FastAPI）。
- 独自ドメインを取得し、Caddy の自動 HTTPS を使う。
- PostgreSQL のポートは外部に公開しない。
- AWS の請求アラートを設定する。

### 実装の準備で決めたこと（2026-10-27）

#### 開発中の動かし方

- 開発中は、画面を Vite の開発用サーバー（`localhost:5173`）で動かし、`/api/` で始まる頼みを Vite から FastAPI（`localhost:8000`）へ中継する。理由：ポート番号が違うとブラウザは別のサイトとして扱い、Cookie が送られないなど本番と違う動きになるため。中継すれば、ブラウザからは画面も API も同じ `localhost:5173` に見え、本番と同じ「同じドメイン」の形になる。画面を直すとすぐ反映される。
- 区切り（プルリクエストの前など）には、本番と同じく「ビルドしたファイルを Caddy が配り、`/api/` を FastAPI に回す」形でも確かめる。
- Cookie の Secure（HTTPS のときだけ送る）は開発中も外さない。ブラウザは `localhost` を安全な場所として扱うので、`http://localhost` でも動く。
- FastAPI と worker は開発中も Docker のコンテナで動かす。`backend/` をコンテナにつなぎ（バインドマウント）、FastAPI は `--reload` で起動して、保存したらすぐ反映させる。
- 開発中だけの設定（フォルダをつなぐ・`--reload`・8000 番を `127.0.0.1` に開ける）は `compose.override.yml` に分け、本番と共通の形は `docker-compose.yml` に置く。本番は `docker-compose.yml` だけで起動する。
- 本番ではコンテナの中を書き換えず、イメージを作り直して入れ替える。
- Node.js は開発とビルドのときだけ使う。本番用の Caddy のコンテナは、Docker のマルチステージビルドで「Node.js でビルドし、できたファイルだけを移す」形にし、Node.js を入れない。

#### フォルダの分け方

```
book-app/
├── docker-compose.yml   4つのコンテナをまとめて起動する
├── .env                 秘密の値（Git に入れない）
├── .env.example         名前とダミーの値だけ（Git に入れる）
├── caddy/               Caddy の設定ファイル
├── backend/             Python（FastAPI と worker が同じコードを使う）
├── frontend/            React＋Vite
└── docs/                設計の文書
```

- 画面とバックエンドは、使う言語・道具・部品がまったく別なので分ける。
- worker は `backend/` に入れる。片付けの関数とテーブルの定義を FastAPI と共有し、同じイメージを起動の命令だけ変えて使うため（api.md 2-8）。
- `docker-compose.yml` と `.env` は一番上に置く。Compose は `backend/` と `frontend/` の両方を使い、`.env` は PostgreSQL のコンテナも読むため。

`backend/` の中は、役割ごとに分ける。

```
backend/
├── pyproject.toml / uv.lock     部品の一覧（uv）
├── Dockerfile                   FastAPI と worker の共通のイメージ
├── alembic/                     マイグレーション
├── app/
│   ├── main.py                  FastAPI の起動。routers をまとめてつなぐ
│   ├── routers/                 受け口（URL ごと）。HTTP の受け渡しだけをし、services を呼ぶ
│   ├── schemas/                 入力・出力の形（Pydantic）
│   ├── services/                アプリの決まりごと（ビジネスロジック）とデータベースの読み書き
│   ├── models/                  テーブルの定義（SQLAlchemy）
│   ├── core/                    どの機能でも使うもの（設定・エラーの形・文字数を数える・ログ）
│   ├── db.py                    データベースへのつなぎ方
│   └── jobs/cleanup.py          worker（5分おきに services の片付けを呼ぶ）
└── tests/                       pytest
```

- 各フォルダの中は、機能ごとのファイルに分ける（例：`routers/books.py`・`services/books.py`）。
- アプリの決まりごとは routers に直接書かず、services に置く。止まった AI提案の片付けを、API（その場の判定）と worker（定期の片付け）の両方から同じ関数で呼ぶため（api.md 2-8）。「自分のものか」の確認も services で行い、どこから呼んでも同じ確認が通るようにする。
- データベースの読み書きだけを集めた層（repositories）は作らない。今の規模ではファイルが増えるだけのため。必要になったら services から分ける。
- 理由：機能が5つの規模では役割ごとに分ける形が分かりやすく、FastAPI の公式の見本とも同じ形のため。機能が大きく増えたら、機能ごとのフォルダに組み替えることもできる。

#### データベースとのやりとり

- 同期で書く（SQLAlchemy の同期の書き方、ドライバは psycopg）。
- 理由：時間がかかるのは OpenAI の呼び出しで、これは受け付けたらすぐ返して裏で進める設計にしている（api.md 2章）。データベースの処理は短く、FastAPI は同期の関数をスレッドプールで並べて動かすので、ほかの利用者を待たせない。非同期は `async`/`await` の付け忘れや、関係するデータを後から読む機能が使えないなどの間違えやすさが増える。
- AI の返事を文字が流れるように画面に出す（ストリーミング）場合や、同時の接続が大きく増えた場合は、非同期への切り替えを考える。

#### 使う道具の版

| 道具 | 版 | 理由 |
| --- | --- | --- |
| Python | 3.14 | 3.15（2026-10-09 リリース）は出たばかりで、依存ライブラリ（Argon2・PostgreSQL のドライバなど）の対応が追いついていない可能性があるため |
| PostgreSQL | 18 | `uuidv7()` を標準で使える最初の版（database.md 2-1）。19 は 2026-10 時点で正式版でない |
| Node.js | 24（24.22.1 以上） | LTS の中心の版。24.22.1 は 2026-10-21 のセキュリティ修正を含む |
| React | 19 | 今の主な版 |

- 最新版ではなく、ライブラリの対応状況と安定性を見て選ぶ。

#### 依存する部品の安全（サプライチェーン攻撃への対策）

- 部品の版を固定する：`package-lock.json` を Git に入れ、`npm ci` で入れる。Python 側は uv を使い、`pyproject.toml`（自分で選んだ部品）と `uv.lock`（裏の部品まで含めた全部の版とハッシュ）を Git に入れ、`uv sync --locked` で入れる。
  - uv を選んだ理由：pip ＋ `requirements.txt` だけでは、裏の部品の版が固定されず、ハッシュでの中身の確認も手作業になり、開発中だけ使う部品（pytest など）も分けにくいため。uv はこの3つをまとめて行い、npm の `package-lock.json`＋`npm ci` と同じ考え方で扱える。
  - 開発中だけ使う部品は `uv add --dev` で入れ、本番のイメージには `--no-dev` で入れない。
  - Python の部品は、`pyproject.toml` の `[tool.uv]` に `exclude-newer = "7 days"` を書き、出てから7日たっていない版を自動で避ける（「出たばかりの版にはすぐ上げない」を道具で守るため。乗っ取られた版はたいてい数日で見つかって消されるので、それより少し長く待つ）。弱点を直した急ぎの版は、部品ごとに `exclude-newer-package` で例外にする。
- npm の部品を入れるときの自動の命令（ライフサイクルスクリプト）を止める（`ignore-scripts=true`）。
- 部品を増やしすぎない。出たばかりの版にはすぐ上げない。
- GitHub の Dependabot で、弱点のある部品を知らせてもらう。

#### 秘密の値（`.env`）

- 秘密の値（データベースのパスワード・JWT の鍵・OpenAI と Google Books の API キー）は `.env` に書き、プログラムは `pydantic-settings` で読む。
- `.env` は `.gitignore` に入れて Git に入れない（リポジトリは公開のため）。名前とダミーの値だけを書いた `.env.example` を Git に入れる。
- 本番（EC2）では、サーバーの上に直接 `.env` を置き、持ち主だけが読める設定（`chmod 600`）にする。Docker のイメージの中には入れない。
- 開発用と本番用で別の値を使う（開発用の鍵が漏れても本番に影響しない）。OpenAI の開発用のキーは、使える金額を小さく決めておく。
- AWS の秘密の値を預けるサービス（Systems Manager Parameter Store など）は、慣れたら移す候補にする。

#### ログ

- 本番は重要度 INFO 以上を出す（DEBUG は開発中だけ）。エラーはスタックトレースも出す。
- 出してよいもの：日時・重要度、API のメソッド・URL・ステータスコード・かかった時間、利用者・本・気づき・AI提案の ID（UUID）、エラーの種類（例外の名前）とエラーコード、AI の呼び出しの成否・時間・トークン数、回数制限やパスワードの再確認の上限に達したこと（WARNING）。
- 出してはいけないもの：パスワード（入力・ハッシュとも）、Cookie・JWT、API キーなどの秘密の値、気づきの本文・引用・AI への回答・AI の返事（利用者の個人的な文章）、メールアドレス（ID で足りる）、接続元の IP（回数制限の表には1日だけ残すが、ログには残さない）。
- 1つの頼みごとにリクエスト ID を付けてログに入れ、1つの頼みの間のログをまとめて探せるようにする。
- ログはコンテナの標準の出力に出し、Docker に任せる（決まった大きさで古いものから消す設定にする）。EC2 が1台のうちは `docker logs` で見て、必要になったら CloudWatch Logs などに集める。
- AI の利用上限額・API キーの誤りは ERROR（api.md 2-6）。
- ログを見られるのは作る側だけで、利用者には見せない（画面の文とは別物）。

#### 土台を作るときに決めたこと（2026-11-19）

- 設定：`backend/app/core/config.py` の `Settings`（pydantic-settings）で環境変数を読み、ファイルの最後で1回だけ `settings = Settings()` を作ってみんなで使う。読めない値があれば、起動の時点でエラーで止まる。接続先は5つの値（`POSTGRES_*`）から `settings.database_url` で組み立て、`.env` に接続文字列を別に書かない（値のもとを1か所にするため）。組み立てには SQLAlchemy の `URL.create()` を使う（パスワードの記号を正しく扱い、表示のときはパスワードが `***` に隠れるため）。
- データベースへのつなぎ方：`app/db.py` に接続（engine）を1つ作り、API の処理ごとに `get_db()` でセッションを渡す。テストでは `get_db()` を差し替えて、テスト用のデータベースにつなぐ。
- 制約とインデックスの名前は、`app/models/base.py` の決まり（naming convention）で自動で付ける。名前が決まっていないと、あとで制約を消す・付け直すマイグレーションが書けないため。
- Alembic の接続先は `alembic.ini` に書かず、`alembic/env.py` で `app/db.py` の接続を使う（接続先の情報を1か所にするため）。開発中は `backend/alembic/` をコンテナにつなぎ、api のコンテナで作った手順のファイルが手元に残るようにする。
- Caddy が受け付けるアドレスは `.env` の `SITE_ADDRESS` で決める。空なら `:80`（手元で `http://localhost` を配る）、本番は独自ドメインを書いて自動の HTTPS にする。
- 画面は TypeScript で書く。理由：画面は AI が書いて人がレビューするため、API の形（api.md）と画面の扱う形のずれを、動かす前に道具で見つけられるようにする。
- Node.js の版は `frontend/.node-version` に書き、nodenv がそれを使う。`package.json` の `engines` と `.npmrc` の `engine-strict=true` で、違う版では部品を入れられないようにする。

#### 機能1（認証）を作るときに決めたこと（2026-11-19）

- エラーの返し方：services は、断るときに `AppError`（ステータスコード・エラーコード・説明を持つ例外。`app/core/errors.py`）を投げる。例外ハンドラーが api.md 1-3 の形に直す。入力の誤り（`RequestValidationError`）・存在しない URL（404）・使えないメソッド（405）・思いがけない失敗（500）も、同じ形にそろえる。
  - 理由：services は worker からも呼ぶので HTTP の返事を作らせたくないが、「何の失敗か」は services が一番よく知っているため。戻り値で失敗を返すと、呼ぶ側すべてに確かめを書く必要があり、書き忘れると失敗が成功として進むため。
- 入力の誤りの `reason`：自分で作る確かめ（`app/core/text.py` など）は、`reason` の名前（`too_long` など）をそのまま誤りの種類にして出す。Pydantic が自動で出す誤りは、`missing` → `required`、`extra_forbidden` → `not_allowed`、決まった値以外 → `invalid_value` のように直す。パスワードの長さの範囲外は `out_of_range`（`min`・`max` 付き）、利用規約に同意していないは `required`。
- 文字数を数える部品：`regex` の `\X`（書記素クラスタ）を使う。`grapheme` は更新が止まっていて、新しい絵文字に対応していないおそれがあるため。
- パスワードも、ほかの入力と同じく前後の空白を除いて NFC にそろえてから、ハッシュ化・照合する（Mac と Windows で同じ文字が別の形で届いても、同じパスワードとして扱うため）。
- 回数制限の同時の押し込み対策：「数える → 1回分を記録する」を、同じ制限・同じ人ごとに PostgreSQL のアドバイザリーロック（`pg_advisory_xact_lock`）で1つずつ通す。失敗だけ数える制限（ログイン）は、先に1回分を記録してからパスワードを確かめ、成功したら記録を消す。
  - 理由：数えてから記録するまでの間に別のリクエストが割り込むと、どちらも「まだ4回」と数えて上限を超えるため。先に記録しないと、同時に10回送られたときに10回ともパスワードを試せてしまうため。
- 新規登録の「同じメールアドレスがないか確かめる → 作る」は、`INSERT … ON CONFLICT (email) DO NOTHING RETURNING` の1回の命令で行う。何も返らなければ 409。
- 接続元の IP：`X-Forwarded-For` の最後の値を使う。Caddy は利用者が送ってきた `X-Forwarded-For` を信用せず、実際の接続元を入れ直して渡すため。本番では FastAPI のポートを外に開けないので、Caddy を通らずに嘘の値を送ることはできない。
- JWT の中身：`sub`（利用者の ID）・`ver`（トークンのバージョン）・`iat`・`exp`。署名は HS256、鍵は `.env` の `JWT_SECRET_KEY`（32文字以上でないと起動しない）。
- テスト：開発用とは別のデータベース（`shiorime_test`）を、テストの最初に自動で作り、本物と同じマイグレーションを当てる。テストごとに全部のテーブルを空にする（同時に押された場合のテストで本当に commit するため、トランザクションを戻す方式は使わない）。pytest は api のコンテナの中で動かす（`docker compose exec api pytest`）。そのため開発用の api のイメージだけ、開発用の部品も入れる（Dockerfile の `INSTALL_DEV`）。
- 時刻の差し替え：日時は `app/core/clock.py` の `now()` からだけ取り、テストではこれを差し替える。freezegun は入れない（部品を増やさないため）。
- Caddy：`/api/` へのリクエストの大きさを 1MB までにした（api.md 5-1）。

#### 機能4（AI提案）のバックエンドを作るときに決めたこと（2026-11-20）

- 回数の +1 は、個人 → アプリ全体の順に、同じトランザクションの中で行う。アプリ全体で断られたら、個人の +1 も一緒に取り消す（ロールバック）。
- 同じ気づきへの開始は、気づきの行をロックして（`SELECT … FOR UPDATE`）1つずつ順番に通す。「処理中か確かめる → AI提案を作る」の間に、同じ気づきへの別の開始が割り込めないようにするため（ほぼ同時に押しても、回数を使うのは1回だけ）。
- 完了の保存は、AI提案の行を「まだ行動プランの作成中なら」の条件付きでロックしてから、前の完了したものを消し、完了にする（1つのトランザクション）。消す・完了にするの2つの操作があるため、1回の UPDATE ではなくロックにした。行がなければ、結果を捨ててログに残す（api.md 7-5 と同じ考え方）。
- OpenAI には Responses API（`responses.parse`）で頼み、`store=False` で利用者の文章を OpenAI 側に保存させない。
- 使う部品：`openai`（OpenAI 公式の Python ライブラリ）。Structured Outputs（Pydantic のモデルで返事の形を決める）と、失敗の種類ごとの例外を使うため。
- テスト：`openai` は `httpx2` を一緒に入れ、FastAPI のテスト用の部品（`TestClient`）は `httpx2` があるとそちらを使う。`httpx2` は同じ名前の Cookie を上書きせずに2つ並べるので、テストで Cookie を入れ替えるときは、先に消してから入れる。

- 「AI提案を受ける」ボタン
- 「AI提案：本日あと◯回（気づきの登録は何件でもできます）」
- 次の一歩（最新の完了したAI提案だけ。1つの気づきに1つ。詳細は screens.md「6. 気づきの詳細」）

### AI提案

1. 深掘りの作成中：「あなたの気づき」を表示し、「AIが質問を考えています…（最大1分ほどかかります）」
2. 深掘りの表示：「AIからの深掘り」、回答の入力欄（◯/500字）、外部AIへの送信の注意書き、「回答して行動プランを受け取る」ボタン
3. 行動プランの作成中：深掘りと回答を表示し、「AIが行動プランを考えています…（最大1分ほどかかります）」
4. 行動プランの表示：行動プラン1〜3個、「気づきに戻る」ボタン（自動で保存済み）

- 3で失敗した場合：エラー文と「もう一度送る（回数は使いません）」ボタン
- 回答を送る前に戻ろうとした場合：要件定義書の確認文を表示（行動プランの作成中は表示しない）
- 深掘りの作成中・回答待ちのAI提案を開き直した場合：「このAI提案は終了しました」と、気づきの詳細画面に戻るボタン

## 8. 設計工程で決めること

### 構成・運用

- フロントエンドの構成（React＋Vite でビルドして Caddy で配信するか）と、開発時の構成（Secure Cookie を含む） → 決定済み（5章「実装の準備で決めたこと」）
- ログに出してよい情報・出してはいけない情報、.env の管理 → 決定済み（5章「実装の準備で決めたこと」）
- DB のバックアップ方法
- プライバシーポリシーに、回数制限のために接続元の IP アドレスを1日記録することを書く（api.md 5-2）

### API

- API のエラーレスポンスの形式とステータスコード → 決定済み（api.md 1章）
- AI提案画面の URL の形式（AI提案ごとに分ける） → 決定済み（api.md 1章・2-4）

### AI 連携・利用制限

- AI 出力のスキーマ、最大出力量、リトライする失敗の分類 → 決定済み（api.md 2-6・2-7）
- 行動プランの作成に失敗した場合の再送信の回数に上限を設けるか → 決定済み（api.md 2-5）
- 行動プランの作成に失敗した後、「もう一度送る」の前に回答を書き直せるか → 決定済み（api.md 2-5）
- 行動プランの保存形式 → 決定済み（database.md 3-4。`jsonb`）
- AIサービス側の月の利用上限額の設定方法（最新の管理画面で、確実に止まる上限として設定できるかを確認する）
- 「2分経過で止まったとみなす」判定と「24時間の後片付け」を、いつ・どの処理で行うか → 決定済み（api.md 2-8）
- アプリ全体の上限に達しているときの「本日の残り回数」の表示 → 決定済み（screens.md「6. 気づきの詳細」）

### 入力・表示

- 文字数の数え方（画面とサーバーで一致させる方法） → 決定済み（api.md 5-1）
- 並び順：本棚、本ごとの気づき一覧、AI提案の履歴 → 決定済み（screens.md。AI提案は1つの気づきに1つだけのため並び順は不要）

### Google Books

- Google Books の扱い：上限を超える長さのタイトル・著者の扱い、APIキーの要否、利用規約上の表示の要否 → 決定済み（api.md 4章）
  - 決定済み（screens.md「2. 本の検索・登録」）：検索はサーバー経由、表紙URLはサーバーで https に直す、検索の回数制限は1人1分10回、出版年は検索結果に表示するだけで保存しない
- Google Books API の利用枠と、枠を超えたときの表示 → 決定済み（api.md 4章）

### 認証・不正利用の防止

- 新規登録の回数制限に達したときの表示文 → 決定済み（screens.md「10. 新規登録・ログイン」）
- ログイン試行・新規登録の回数制限で、何を数えるか → 決定済み（api.md 5-2）
- パスワード変更・退会時のパスワード再入力に、回数制限を設けるか → 決定済み（api.md 5-2）

### 画面遷移

- ログイン画面と新規登録画面の相互の移動、ログイン中にログイン画面を開いた場合の扱い → 決定済み（screens.md「10.」、api.md 3-4・3-5）
- ログイン後に利用規約・プライバシーポリシーを見られる場所 → 決定済み（screens.md「9.」）
- 気づきの編集中にログインの期限が切れた場合の扱い → 決定済み（api.md 3-6）

### 規約・プライバシー

- 利用規約への同意日時を記録するか → 決定済み（database.md 3-1。`terms_agreed_at`）
- プライバシーポリシーの記載事項（運営者の連絡先、外国にある第三者への提供の扱い、OpenAI 側でのデータ保持期間など。最新の法令・規約を確認する）
