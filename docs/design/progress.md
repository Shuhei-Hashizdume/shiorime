## 3. 詳細設計で決めること（画面設計レビューの持ち越し）

画面だけでは決めきれず、API・データベースと一緒に決める必要があるもの。**どれも未決。api.md・database.md を作るときに必ず決め、決めたら screens.md の該当箇所にも反映する。**

### 3-1. 行動プランの作成中に、気づきの詳細を開いたときの表示

**決定（2026-10-23）**：api.md 2-3 と screens.md「6. 気づきの詳細 › 行動プランの作成中・完了・失敗」に反映済み。

- 状況：AI提案画面で回答を送ったあと（状態＝行動プランの作成中）に画面を離れ、気づきの詳細を開いた場合。要件定義書は「完了すると、気づきの詳細に表示されます」と案内しているが、気づきの詳細の設計（screens.md「6.」）に、作成中の表示がない。
- 決めること：
  - 作成中であることの表示（例：次の一歩の場所に「次の一歩を作成中です…」）。
  - 完了を画面にどう反映するか（一定の間隔で状態を問い合わせるか、開き直したときだけか）。問い合わせるなら間隔と止める条件。
  - 作成中に「もう一度AI提案を受ける」を押せるか（要件では処理中は始められない。押したときの表示を決める）。
  - 裏で作成に失敗した場合：要件定義書 10章の既知の制限では「画面を離れていた場合は残らない」。notes.md 2章の後片付け（2分で止まったとみなす・24時間で削除）と合わせて、気づきの詳細で何も知らせないのか、「作成できませんでした」と一度知らせるのかを決める。
- 関係：requirements.md 5.5、notes.md「2. 競合対策」、screens.md「6. 気づきの詳細」「8. AI提案」。

### 3-2. 「もう一度送る（回数は使いません）」の回数の上限

**決定（2026-10-23）**：上限（3回）・上限に達したときの扱い・書き直しは api.md 2-5 と screens.md「8.」、自動の再試行の分類は api.md 2-6 に反映済み。

- 状況：行動プランの作成に失敗したとき、画面にいれば回数を使わずに送り直せる（要件定義書 5.5）。今は上限がなく、AIの呼び出しに失敗しても料金がかかる場合があるため、料金の穴になる。notes.md 8章でも未決。
- 決めること：
  - 1つのAI提案で送り直せる回数（案：3回まで）。
  - 上限に達したときの表示と、そのAI提案の扱い（例：「時間をおいて、気づきの詳細から新しく始めてください」と表示し、AI提案は終了。使った1回は戻らない／戻す）。
  - どの失敗を自動で再試行し、どの失敗を利用者の「もう一度送る」に任せるか（notes.md 8章「リトライする失敗の分類」）。
  - 「もう一度送る」の前に回答を書き直せるか（notes.md 8章の未決）。
- 関係：screens.md「8. AI提案 › 失敗したとき」、requirements.md 6章（回数制限）。

### 3-3. 「AI提案を受ける」を押したとき、サーバーに断られた場合の表示

**決定（2026-10-23）**：api.md 2-4、screens.md「6. 気づきの詳細 › 押して断られた場合」、要件定義書の既知の制限に反映済み。受付番号（冪等キー）による送り直しを追加（database.md で欄と制約を書く）。

- 状況：気づきの詳細では、画面を開いたときの残り回数でボタンを出し分けるが、押した時点で状況が変わっていることがある（日付が変わった・別の端末で使い切った・アプリ全体の上限に達した・同じ気づきのAI提案を処理中・通信の失敗）。
- 決めること：
  - それぞれの理由をサーバーがどう返すか（エラーの種類とステータスコード）。
  - 画面での表示場所（案：気づきの詳細に残る形で、ボタンの近くに表示し、ボタンの表示も最新の状態に直す）と文言。文言は screens.md「6.」の表の文にそろえる。
  - AI提案画面へ移る前に断るのか、移ってから表示するのか（URL はAI提案ごとに分ける決まりなので、作れなかった場合は移らない案が自然）。
- 関係：screens.md「6. 気づきの詳細 › AI提案のボタンと確認」。

### 3-4. ログインしていない場合と、ログインの期限切れの見分け方

**決定（2026-10-23）**：api.md 3章に反映済み。Cookie は30日・JWT は7日、`TOKEN_EXPIRED`・`TOKEN_REVOKED` で見分ける。

- 状況：要件定義書 9章は「ログインしていない人の最初の画面はウェルカム」「ログインしていない、または期限切れの場合はログイン画面へ」としているが、使い分けが曖昧。ログインは httpOnly の Cookie（7日）なので、Cookie の期限が切れて消えると、サーバーからは「ログインしていない」と「期限切れ」の区別がつかない可能性がある。
- 決めること：
  - どの場合にウェルカムへ、どの場合にログイン画面へ移すか（案：トップの URL を開いた未ログインの人はウェルカム、ログインが必要な画面を開いた未ログインの人はログイン画面）。
  - 「ログインの有効期限が切れました」のお知らせを出す条件と、判定方法（例：画面側に「ログインしたことがある」印だけを残し、API が未認証を返したときにその印があれば期限切れとみなす）。
  - ログイン中にウェルカム・ログイン・新規登録の画面を開いた場合の扱い（ウェルカムは本棚へ移す、と screens.md「11.」で決め済み。ログイン・新規登録も本棚へ移すかを決める）。
  - ログイン後の戻り先の渡し方（アプリ内のパスだけを受け付ける、は screens.md「10.」で決め済み）。
- 関係：requirements.md 9章、notes.md 8章（画面遷移の未決分）、screens.md「10.」「11.」。

### 3-5. 書いている途中でログインの期限が切れた場合に、書いた文を失わない方法

**決定（2026-10-23）**：その場のシートでログインし直し、成功したら自動で送り直す。api.md 3-6 に反映済み。

- 状況：気づきの作成・編集（最大1000字）や、AI提案の回答（最大500字）を書いている間に期限が切れると、保存・送信したときに未認証になり、ログイン画面へ移って文が消える。notes.md 8章でも未決。
- 決めること（案のどれか、または組み合わせ）：
  - 未認証を返されたら、画面を移さずに「ログインの有効期限が切れました。もう一度ログインしてから保存してください」と表示し、入力内容を画面に残す。ログインは別の画面（またはシート）で行い、戻ってから保存し直せるようにする。
  - 書きかけの内容を一時的に端末のブラウザに残す（下書きは MVP では作らない決まりなので、期限切れのときだけに限るか検討）。
  - 書いている間は期限を延ばす仕組み（第2段階のリフレッシュトークンと関係する）。
- 関係：screens.md「7. 気づきの作成・編集」「8. AI提案」、requirements.md 10章（既知の制限）。

## 4. 主な決定事項（詳細は各文書）

- 名前：SHIORIME（しおりめ）。キャッチコピー「今夜の栞を、明日の芽に。」
- 見た目：夜「夜の読書灯」／朝「朝日の差す机」。書体はすべてキウイ丸（太さ400・500、太字なし）、ロゴの「SHIORIME」だけ Zen 丸ゴシック（SVG で用意）。引用は紙片で表す。灯りの色で塗るのは押すボタンだけ。
- 画面：12画面＋モーダル2つ（screens.md の目次）。気づき一覧は0件の本も出し、並び順は3つ。本の編集は手入力の本だけ。
- AI提案：1つの気づきに残すのは最新の完了した1つだけ（完了時に置き換え）。1人1日5回、アプリ全体で1日100回。AIは OpenAI を使う（料金を Claude と比べ、最新の最安モデルどうしは同じ価格だったため、買ってあるクレジットを使う）。モデル名は詳細設計で決める。
- トースト：15文字まで2秒、16文字以上2.5秒。成功の知らせだけ。

## 5. 作業の決まり（このプロジェクトの進め方）

- 要件定義 → 基本設計 → 詳細設計 → 実装の順。前回の反省（要件を決めずに15機能を作って混乱した）から、決めてから作る。
- 仕様書を作ったら、サブエージェントにレビューさせて抜け漏れを確かめる。
- 提案は4つの視点（利用者・作る側・セキュリティ・将来の拡張）で確かめてから出す。数値には理由を残す。
- AI が作ったように見える見た目を避ける（絵文字・左側の線で強調・Lucide アイコンを使わない）。
- 決まった画面・見た目は docs/design/ に入れてコミットする。
- コミット：`git status` → `git add .` → `git status` → `git commit -m "docs: ..."` → `git push`。コミットのメールアドレスは GitHub の noreply（設定済み）。GitHub への push は Cursor のターミナルから行う（Claude の作業環境からは GitHub に接続できない）。
