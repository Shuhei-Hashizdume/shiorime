# SHIORIME API 設計書

画面（React）とサーバー（FastAPI）の間の決まり（エンドポイント・入出力・エラー・認証・回数制限）をまとめる。画面の動きは [screens.md](screens.md)、要件は [要件定義書](../requirements.md)、技術的な決定は [notes.md](notes.md) を参照。

**作成中**：決めた順に書き足している。進み具合は [progress.md](progress.md) を参照。

## 1. 共通の決まり

### 1-1. URL

- すべての API は `/api/v1/` で始める（例：`/api/v1/books`）。
  - `/api`：画面と API を同じドメインから配信するため、Caddy が `/api` で始まる要求だけを FastAPI に振り分ける目印。
  - `v1`：API の版。返す形を大きく変えるとき（例：次の一歩を文の並びから「文＋やったか」の形に変える）に `v2` を作れば、公開作業の瞬間に開いていた古い画面や、将来のスマートフォンアプリが壊れない。今付ける手間は設定1か所だが、後から付けるとすべての URL を書き換える必要があるため、最初から付ける。

### 1-2. ID の形式

- 本・気づき・AI提案・ユーザーの ID は UUID にする（連番にしない）。
- 理由：
  - 第3段階で読了投稿の公開を予定しており、URL が外に出る。連番だと件数や利用者数を推測でき、後から UUID に変えるとすべての表のつながりと URL を作り直す必要がある。
  - 他人のデータを見られないかの確認を1か所でも書き忘れた場合、連番では番号を1つずつ変えるだけで他人の気づきを見られるが、UUID では他人の ID を当てられないため被害が出にくい（作る側のミスに対する保険）。
- 欠点として URL が長くなり、開発中に目で追いにくいが、利用者が URL を入力することはなく、並び順は作成日時で決めているため影響しない。

### 1-3. エラーの形

```json
{
  "error": {
    "code": "AI_DAILY_LIMIT",
    "message": "開発者向けの説明（画面には出さない）"
  }
}
```

- 画面に出す文言は、画面側が `code` を見て決める（文言は screens.md で決めており、サーバーにも書くと2か所で食い違う原因になるため）。
- 入力の誤り（422）は、項目ごとの誤りの一覧を `error.fields` に付ける（形は後で決める）。
- FastAPI 標準の `{"detail": ...}` の形は使わず、例外ハンドラーでこの形にそろえる。

### 1-4. ステータスコード

| 番号 | 意味 | 例 |
| --- | --- | --- |
| 200 / 201 / 204 | 成功（取得・変更 / 作成 / 返すものなし） | ー |
| 401 | ログインしていない・期限切れ | Cookie がない、JWT の期限切れ |
| 404 | 見つからない（**他人のものも含む**） | 存在しない本、他人の気づき |
| 409 | 今の状態と合わない | 同じ本の二重登録、同じ気づきの AI提案を処理中 |
| 422 | 入力が正しくない | 気づきの本文が1001文字 |
| 429 | 回数の上限 | AI提案の6回目、ログイン試行の6回目（種類は `code` で区別） |
| 502 | 外部サービスの失敗 | OpenAI・Google Books が応答しない |
| 500 | そのほかのサーバーの失敗 | ー |

- 403（あるが見せない）は使わない。他人のものがあることを知らせないため、すべて 404 にする。

### 1-5. 一覧の続きの読み込み

```json
{
  "items": [ ... ],
  "next_cursor": "続きの位置（続きがなければ null）"
}
```

- 画面は、下までスクロールしたら `next_cursor` を付けて続きを頼む。`next_cursor` が null なら続きはない。
- 何件目からかを番号で渡す方式にしない理由：読み込みの途中で本を追加・削除すると、同じ本が2回出たり飛ばされたりするため。

### 1-6. 項目名の書き方

- JSON の項目名はスネークケース（`agreed_to_terms` の形）にそろえる。理由：サーバー（Python・Pydantic）の書き方と同じで変換が要らず、FastAPI が自動で作る API の説明書（`/docs`）も同じ書き方になるため。画面（TypeScript）はそのまま受け取る。
- 決まった値の中から選ぶ項目（属性など）は、日本語ではなく記号で送る。日本語の表示名は画面が持つ（エラーコードと同じ考え方）。

## 2. AI提案の処理の進め方（非同期処理＋ポーリング）

AI の応答は数秒〜最大約60秒（30秒×再試行1回）かかるため、AI を呼ぶ操作は、受け付けたらすぐ返し、AI はサーバーの裏で呼ぶ（非同期処理）。画面は一定の間隔で状態を問い合わせる（ポーリング）。

### 2-1. 流れ

```
画面   → POST /api/v1/ai-proposals/{id}/answer（回答を送る）
サーバー → 202 Accepted（受け付けた。まだ終わっていない）
         裏で AI を呼ぶ（状態：行動プランの作成中）
画面   → GET /api/v1/ai-proposals/{id}（2秒ごと）
サーバー → 200（状態：行動プランの作成中）
   …
サーバー → 200（状態：完了、次の一歩）
```

- AI提案の開始（深掘りの作成）も同じ流れにする。
- 問い合わせの間隔は2秒。
  - 理由：AI は数秒〜十数秒で答えることが多く、間隔が長いと、できているのに待たされる。2秒なら遅れは最大2秒。最大60秒待っても問い合わせは30回で、一覧の取得より軽い処理のため負担は小さい。
- 問い合わせを止める条件：状態が完了・失敗などの結果になったとき、画面を離れたとき。

### 2-2. この方式にした理由

- 決め済みの「回答を送った後に画面を離れても作成を続けて保存する」「開き直すと作成中と表示する」を実現するため。その場で待つ方式（同期処理）では、画面を離れたり通信が切れたりすると要求が切れ、作成が止まるおそれがあり、作成中かどうかを確かめる手段もない。
- 裏の処理は FastAPI の BackgroundTasks で行い、ジョブキュー（Celery＋Redis など）は使わない。
  - 理由：MVP の利用規模ではコンテナを増やすほどの必要がなく、サーバーの再起動で処理が失われても、notes.md の「2分たったら止まったとみなす」決まりで片付けられるため。
  - 見直すきっかけ：利用者が増えて、裏の処理が API の応答を遅くするようになった場合。
- サーバーから完了を知らせる方式（WebSocket・Server-Sent Events）は使わない。
  - 理由：作るのが難しく、2秒のポーリングで足りるため。
- 問い合わせ（GET）も、自分の AI提案かを確かめてから答える（他人のものは 404）。

### 2-3. 行動プランの作成中に、気づきの詳細を開いたとき

見本：[mockups/notedetail-making.html](mockups/notedetail-making.html)

- 気づきの取得（`GET /insights/{id}`）は、その気づきで「行動プランの作成中」のAI提案があれば、その ID と状態も返す。
- **表示**：前の次の一歩は消さずに残し、その下に芽が育つ動きと「新しい次の一歩を作成中です…／完了すると、ここに表示されます」。前の次の一歩がなければ「次の一歩を作成中です…」だけ。
  - 理由：新しいAI提案は完了したときだけ前のものと置き換わり、完了しなかったら前のものが残る決まり（要件定義書 5.5）。作成中に前のものを消すと、失敗したときに消えたものが戻ってくる動きになり、わかりにくいため。
- **完了の反映**：気づきの詳細を開いている間も、AI提案画面と同じく2秒ごとに `GET /ai-proposals/{id}` で状態を問い合わせる。完了したら新しい次の一歩に置き換え、トースト「次の一歩ができました」。
  - 止める条件：状態が「行動プランの作成中」でなくなったとき（完了・失敗・削除）、画面を離れたとき。
  - タブが裏にある間は一時停止し、表に戻したら再開する（見ていない画面への問い合わせをなくすため。Page Visibility API）。
  - 念のための上限：画面を開いてから3分で問い合わせをやめる。理由：サーバーが2分で止まったとみなすため通常はそれより先に終わるが、不具合で状態が変わらなかったときに問い合わせ続けないため（2分＋余裕1分）。
  - 問い合わせの部品は AI提案画面と共通にする。
- **ボタン**：作成中は最初から押せない見た目にし、文を「AI提案を処理中です」にする（aria-disabled）。
  - 理由：押してから断られるより、押す前に始められないことがわかるほうが迷わないため。作成中かどうかは問い合わせで常に把握しているので、追加の手間はほぼない。
  - 画面の表示が古い場合（別のタブで始めたなど）に備え、開始時はサーバーで必ず確かめる。断られた場合の表示は 2-4 で決める。
- **失敗した場合**：前の次の一歩は残し、ボタンの上に「次の一歩を作成できませんでした／使った回数は戻りません。もう一度AI提案を受けられます。」（夕焼けの枠と記号。色だけで伝えない）。ボタンは押せる状態に戻す。
  - 失敗の見分け方：状態が「回答待ち」で、回答が入っているAI提案は、行動プランの作成に失敗したもの（新しい項目を足さずに判定できる）。気づきの取得でこれも返す。
  - 表示が消えるのは、新しいAI提案を始めたとき（回答待ちのものは開始時に削除する決まり）か、24時間の後片付けのとき。
  - 回数が戻らないことを書く理由：要件定義書の既知の制限のとおりで、隠すと残り回数が減っている理由がわからなくなるため。
  - 失敗したAI提案を気づきの詳細から送り直す仕組みは作らない（要件定義書「失敗したAI提案を後から再開しない」のとおり）。

### 2-4. AI提案を始めるとき、サーバーに断られた場合

見本：[mockups/refused.html](mockups/refused.html)

- 「AI提案を受ける」を押したら、まず `POST /insights/{id}/ai-proposals` で AI提案を作り、成功（202、AI提案の ID が返る）してから AI提案の画面 `/ai-proposals/{id}` へ移る。断られた場合は移らず、気づきの詳細で理由を知らせる。
  - 理由：AI提案の画面は AI提案ごとに URL を分ける決まりで、断られた場合は移る先の ID がないため。移ってから断ると、画面が2回切り替わってわかりにくいため。
  - 返事を待つ間（ふつう1秒未満。AI を呼ぶのは移った後）、ボタンを「準備しています…」にして押せなくする（二重送信の防止）。
- 断られたときは、ボタンの上にお知らせを出し、ボタンと残り回数の文も最新の状態に直す。

| 理由 | 返すもの | お知らせ | ボタン・下の文 |
| --- | --- | --- | --- |
| 本人の回数を使い切った | 429 `AI_DAILY_LIMIT` | AI提案を始められませんでした／本日の回数を使い切っています（ほかの端末で使った分も含みます）。 | 押せない見た目、「本日のAI提案は使い切りました。明日0時に回復します。」 |
| アプリ全体の上限 | 429 `AI_APP_LIMIT` | AI提案を始められませんでした／本日はAI提案の受付を終了しました。 | 押せない見た目、「本日はAI提案の受付を終了しました。明日0時に再開します。」 |
| 同じ気づきのAI提案を処理中 | 409 `AI_PROPOSAL_IN_PROGRESS` | この気づきのAI提案を処理中です／しばらくお待ちください。 | 2-3 の作成中の表示に切り替え、問い合わせを始める |
| 気づきが見つからない | 404 `INSIGHT_NOT_FOUND` | ー | 画面全体を「この気づきは見つかりませんでした」に切り替える |
| 通信・サーバーの失敗 | 通信の失敗／500 | AI提案を始められませんでした／通信に失敗しました。時間をおいて、もう一度お試しください。 | 押せるまま。気づきを読み込み直して残り回数を最新にする |

- お知らせの枠は、決まりどおりに止まった場合（回数・上限・処理中）は落ち着いた色、本当に失敗した場合（通信・サーバー）だけ夕焼けの色にする。理由：決まりで止まったものを不具合のように見せないため。
- 「ほかの端末で使った分も含みます」と書く理由：画面に「あと2回」と出ていたのに断られると、数え間違いと思われるため。
- 通信の失敗のお知らせに「回数は使っていません」とは書かない。理由：頼みがサーバーに届いて回数を使った後に、返事だけが届かなかった場合があり、画面からは見分けられないため。

#### 受付番号（冪等キー）による送り直し

- スマートフォンとサーバーの間で返事が届かなかった場合、サーバーは回数を使って AI提案を作り終えているのに、利用者は質問を受け取れない（回数だけ減る）ことがある。サーバーからは返事が届かなかったことがわからないため、サーバー側では回数を戻せない（AI との間の失敗は、サーバーが気づけるので回数を戻す。こちらは決め済み）。
- 対策として、AI提案の開始に受付番号（冪等キー）を付ける。
  - 画面：押したときに受付番号（UUID、`crypto.randomUUID()`）を作り、`Idempotency-Key` ヘッダーで送る。返事が届かなかったら、同じ番号で1回だけ自動で送り直す。
  - サーバー：作る前に、その利用者が同じ番号で AI提案を作っていないかを確かめる。あれば回数を増やさず、そのAI提案を返す（202）。なければ通常どおり回数を+1して作る。
  - データベース：AI提案に受付番号の欄を持たせ、「利用者＋受付番号」に一意の制約を付ける。ほぼ同時に2つ届いて確かめをすり抜けた場合は、2つ目が制約違反になるので、既にあるものとして返す（database.md に書く）。
  - 同じ番号で深掘りの作成に失敗して終わった AI提案（`question_failed`）が見つかった場合も、それを返す（202）。画面は問い合わせで失敗を知り、「AIの質問を作成できませんでした」を出す。番号が見つからない場合（24時間の後片付けで消えたなど）は、新しく作る。失敗した方は回数を戻しているので、二重には使わない。
  - テスト：同じ番号で2回送っても回数は1回しか減らず、AI提案も1つだけ作られること。同時に送った場合も同じであること。
- 送り直しも失敗した場合は、回数だけ減ることがある（既知の制限。作られた AI提案は回答待ちのまま、次の開始時か24時間の後片付けで削除される）。
- 理由：手間は欄1つと確認処理だけで小さいわりに、利用者が質問を見ていないのに回数を失う損をなくせるため。

### 2-5. 「もう一度送る」（行動プランの作成に失敗したときの送り直し）

見本：[mockups/resend.html](mockups/resend.html)・[mockups/editans.html](mockups/editans.html)

- `POST /ai-proposals/{id}/retry`。送り直しでは1日の回数を使わない（要件定義書 5.5）。
- **上限**：1つのAI提案につき送り直しは3回まで（最初の送信と合わせて最大4回）。
  - 理由：今のままでは送り直しに上限がなく、回数は減らないのに OpenAI の料金だけ増え続ける穴になるため。一時的な失敗なら1〜2回の送り直しで直ることが多く、3回続けて失敗するならAIのサービス自体が止まっている可能性が高いため。AIの呼び出しは1つのAI提案あたり最大8回（4回の送信×自動の再試行込み2回）に収まり、料金を見積もれる。
  - 送り直した回数はAI提案に持たせ、サーバーで数える（画面の操作ですり抜けられないようにするため）。+1 と上限の確認は DB への1回の命令で行う。
  - 送り直すたびに、ボタンの下に「送り直せるのは、あと◯回です」と出す（いつまで押せばよいかがわかるようにするため）。
- **上限に達したとき**：このAI提案を終了（状態を `retry_limit_reached` にする。すぐには削除せず、24時間の後片付けで消す。7-6）し、本人の回数を1回戻す。アプリ全体の回数は戻さない。画面は「次の一歩を作成できませんでした／AIが応答しない状態が続いているため、このAI提案は終了しました。本日の回数は1回戻しています。時間をおいて、気づきの詳細から新しく始めてください。」と「気づきに戻る」。
  - 本人の回数を戻す理由：失敗はAI側の原因で、利用者は回答を送って次の一歩を待っていただけのため（送り直しで回数を使わないのと同じ考え方）。回答前に画面を離れた場合（回数は戻らない）は利用者の都合で終わったもので、わざと失敗させて得をすることはできないため、ぶつからない。
  - アプリ全体の回数を戻さない理由：料金の歯止めのため。戻すと、AIが不調な日に「始める→4回送る→失敗→戻る」を何度でも繰り返せてしまう。1日の料金の上限は、100回×AIの呼び出し最大10回（深掘り2回＋行動プラン8回）のまま変わらない。
  - 状態の変更（`retry_limit_reached`）と本人の回数の −1 は1つのトランザクションで行い、そのAI提案がまだ行動プランの作成中の場合だけ行う（決め済みの競合対策と同じ）。
- **書き直し**：送り直す前に回答を直せる。送った回答を入力欄に戻し、直さずに押せばそのまま送り直す。
  - 理由：失敗の多くは回答と関係ないが、まれに回答の中身が原因（AI側の安全確認で断られる、短すぎて次の一歩を作れないなど）の場合があり、そのときは同じ回答では何度送っても失敗するため。
  - 保存されている回答は、送り直したときの内容で上書きする（見返しでは最後に送った回答を表示）。
  - 入力の確認は最初の送信と同じ（1〜500文字、前後の空白を除いて数える）。サーバーでも確かめる。
  - 送り直せるのは失敗したときだけで、上限3回も変わらないため、料金の穴にはならない。

### 2-6. AI の呼び出しで自動の再試行をする失敗

- AI の呼び出しが失敗したら、サーバーが1回だけ自動で再試行する（要件定義書 7章）。再試行するのは一時的な失敗だけで、何度やっても同じ失敗は再試行しない。仕分けは OpenAI の公式の説明（エラーごとの再試行の要否）に合わせる。

| 失敗 | Python ライブラリの例外 | 自動の再試行 |
| --- | --- | --- |
| 時間切れ（30秒） | `APITimeoutError` | する |
| OpenAI 側の不調（500・503） | `InternalServerError` | する |
| 回数制限（429、`error.code` が回数制限） | `RateLimitError` | する |
| サーバーと OpenAI の間の通信の失敗 | `APIConnectionError` | する |
| 返事の形が決まりと違う（次の一歩が1〜3個でない、など） | （自分たちの出力のバリデーション） | する（AI の答えは毎回少し違い、やり直せば正しい形になることが多いため） |
| 利用上限額・クレジット切れ（429、`error.code` が料金上限） | `RateLimitError` | しない（上限額を上げるまで直らないため） |
| API キーの誤り・使えない地域（401・403） | `AuthenticationError` など | しない（設定を直すまで直らないため） |
| 頼み方の誤り（400） | `BadRequestError` | しない（プログラムの不具合のため） |
| AI が内容を理由に断った | ー | しない（同じ回答では同じ結果になるため。利用者が回答を直して送り直す。2-5） |

- 再試行の前に1秒待つ。OpenAI から `Retry-After` で待ち時間を指示された場合はその秒数を待つが、5秒を超えるなら再試行せずに失敗とする。
  - 理由：すぐ再試行すると混雑が続いていることが多いため。長く待つと、利用者の最大の待ち時間（約60秒）を超えるため。
- OpenAI の Python ライブラリの自動の再試行はオフにし（`max_retries=0`）、時間切れも明示する（`timeout=30`）。
  - 理由：ライブラリは初期設定で自分でも再試行するため、こちらの再試行と重なり、AI の呼び出し回数（料金の上限の計算：1つのAI提案で最大10回）と待ち時間の計算が狂うため。再試行の判断は自分たちのコードの1か所にまとめる。
- 利用上限額・API キーの失敗は、作る側が直す必要がある失敗なので、ログに重要度「エラー」で残す。利用者への表示は、ほかの失敗と同じ（2-4・2-5・screens.md）。
- テスト：OpenAI を偽物に置き換え、一時的な失敗では1回だけ再試行すること、恒久的な失敗では再試行しないことを確かめる。

### 2-7. AI の出力の形式と、出力の最大量

- AI には決まった形（JSON）で答えさせる（OpenAI の Structured Outputs。Python では `client.responses.parse` に Pydantic のモデルを `text_format` として渡す）。理由：文章から質問や次の一歩を読み取る処理が要らず、形の崩れがほぼ起きないため。

深掘り（AI からの質問）
```json
{ "question": "黙ってしまう直前、頭の中ではどんな言葉が浮かんでいますか？" }
```

次の一歩（行動プラン）
```json
{ "plans": [ { "text": "次の会議で、結論から一言だけ発言する" }, { "text": "発言したあとの気持ちを1行メモする" } ] }
```

- 次の一歩の1つずつは、文字列ではなく `{"text": …}` の形にする。理由：第2段階で「やった」チェックなどを足すときに `{"text": …, "done": false}` と項目を足すだけで済み、API の版を上げずに古い画面を壊さないため。
- 長さの上限：質問は200文字、次の一歩は1つ100文字・1〜3個。プロンプトでは「質問は100文字程度」「1つ50文字程度」と短めに頼み、上限には余裕を持たせる。理由：画面で読みやすい長さに収めるため。
- 受け取った後、サーバーの Pydantic で形と長さを必ず確かめる。外れたら「返事の形が決まりと違う」失敗として1回だけ自動で再試行する（2-6）。理由：形の指定だけでは、文字数や個数の上限まで確実に守られるとは限らないため。
- 出力の最大量（`max_output_tokens`）：深掘り300、次の一歩600。理由：日本語は1文字がおよそ1トークン以上になるため、上限の文字数に余裕を持たせた値にした。1回あたりの料金が頭打ちになり、1日の料金の上限（全体100回×呼び出し最大10回×1回の最大量）を計算できる。
- 最大量で答えが途中で切れた場合（レスポンスが incomplete）は、「形が違う」失敗と同じく1回だけ再試行する。
- AI が断った場合（refusal）は再試行しない（2-6）。利用者が回答を直して送り直す（2-5）。
- 使うモデルは `.env` の `OPENAI_MODEL` で指定し、コードに書かない。理由：料金や性能を見て、コードを変えずに切り替えられるようにするため。どのモデルにするかは実装時に料金を見て決める。
- テスト：偽物の OpenAI が、正しい形・個数が0や4・文字数超え・途中で切れた答え・拒否を返す場合を試す。

### 2-8. 止まった AI提案の片付けを動かす処理

- 片付けの対象（要件定義書のとおり）：
  - 深掘りの作成中のまま2分たったもの → 状態を `question_failed`（深掘りの作成に失敗して終わった）にし、個人とアプリ全体の回数を戻す（すぐには削除しない。7-6）。
  - 行動プランの作成中のまま2分たったもの → 回答待ちに戻す。
  - 回答待ちのまま24時間たったもの → AI提案を削除する（回数は戻らない）。
  - 失敗して終わったもの（`question_failed`・`retry_limit_reached`）のまま24時間たったもの → AI提案を削除する（回数は失敗したときに戻し済み）。
- 理由：サーバーの再起動などで裏の処理が消えると、AI提案が作成中のまま止まり、回数が戻らない・同じ気づきで新しく始められない・データが残り続ける、ということが起きるため。

#### その場の判定と、5分おきの片付けの2本立て

| 場面 | 片付ける処理 |
| --- | --- |
| 利用者が見ている（AI提案の状態の確認、気づきの詳細、AI提案の開始、回答の送信、残り回数の表示） | その場で判定する。2分（回答の送信は24時間）を過ぎていれば、その場で止まった扱いにしてから答える |
| 誰も見ていない | 5分おきに動く片付けの処理がまとめて拾う |

- その場の判定だけでは、ブラウザを閉じた後にサーバーが再起動した場合などに誰も状態を聞きに来ず、回数が戻らないため、定期の片付けも置く。定期の片付けだけでは、画面で待っている利用者が、止まったとわかるまで最大で7分ほど待たされるため、その場の判定も置く。
- 残り回数を出す API は、その人の止まった AI提案を先に片付けてから回数を返す（戻るはずの回数が減ったまま表示されないようにするため）。
- 5分の理由：利用者が見ている場面はその場の判定で拾えるため、定期の片付けは誰も見ていない分の保険でよい。回数を戻すのが遅れすぎないよう短めにしつつ、1分おきほど頻繁にする必要はないため。
- 片付けは「まだ深掘りの作成中なら `question_failed` にして回数を戻す」などを DB への1回の命令で行う（notes.md 2章の競合対策と同じ）。その場の判定と定期の片付けが同じ AI提案を同時に片付けようとしても、回数を2回戻すことはない。
- 片付けの処理は関数1つにまとめ、その場の判定と定期の片付けの両方から呼ぶ。
- 24時間を過ぎた後に回答を送った場合は、削除がまだでもその場で「このAI提案は終了しました。気づきの詳細から新しく始めてください」を返す（要件定義書のとおり）。
- テスト：その場の判定と定期の片付けを同時に動かしても回数は1回しか戻らないこと。2分・24時間の境目（時刻を差し替えて確かめる）。

#### 定期の片付けを動かす場所

- Docker Compose に片付け専用のコンテナ（`worker`）を足し、4つのコンテナ（Caddy・FastAPI・片付け・PostgreSQL）にする。FastAPI と同じイメージを使い、起動の命令だけを `python -m app.jobs.cleanup`（5分おきに片付けを動かし続ける）に変える。
- 外には何も公開しない（Caddy からもつながない）。`restart: unless-stopped` で、止まったら自動で立ち上げ直す。処理した件数と失敗はログに残す。
- この形にした理由：
  - 片付けを API と同じ Python のコードで書け、その場の判定と同じ関数・同じテストを使えるため（PostgreSQL の pg_cron は SQL で別に書くことになるため使わない）。
  - ローカルも本番と同じ Docker Compose で動き、「ローカルも本番と同じ構成」を守れるため（EC2 の cron は使わない）。
  - 片付けが失敗しても API が止まらず、ログも分かれるため（FastAPI の中で APScheduler などで動かす形は使わない。FastAPI を複数動かすと片付けも複数動く問題もある）。
- 将来、メール送信など裏の処理が増えたらこのコンテナに足す。さらに増えたらジョブキュー（Celery など）に置き換える。

## 3. ログイン状態の判断と画面の移り方

### 3-1. 画面がログイン状態を知る方法

- JWT は HttpOnly の Cookie に入れるため、画面の JavaScript からは読めない（XSS で盗まれにくくするため）。画面は開いたときに `GET /api/v1/me` を呼び、200 ならログイン中、401 なら未ログインとして扱う。ログインしているかを判断するのは常にサーバーで、画面の出し分けは見た目のためだけ。

### 3-2. 未ログインの人を移す先

| 未ログインの人が開いた画面 | 移る先 |
| --- | --- |
| トップ（`/`） | ウェルカム（初めての人に、まず何のアプリかを伝えるため） |
| ログインが必要な画面 | ログイン画面（戻り先を付ける。URL を直接開いた人は既に使っている人である可能性が高く、ウェルカムを挟むと1手間増えるため） |
| 利用規約・プライバシーポリシー | そのまま表示 |

- 期限切れ・パスワード変更で無効（下の 3-3）とわかった人がトップを開いた場合は、ウェルカムではなくログイン画面へ移す（既に使っている人だとわかっているため）。

### 3-3. 期限切れの見分け方

- Cookie の期限（Max-Age）は30日、JWT の期限（exp）は7日にする。7日を過ぎても Cookie は残るので、サーバーは「期限切れの JWT が届いた」とわかる。
  - 30日の理由：7日を過ぎてからしばらくぶりに開いた人にも、期限切れのお知らせを出せるようにするため。長すぎると使い終わった Cookie がいつまでも残るため、JWT の期限の約4倍で区切った。
  - Cookie が30日残っても、中の JWT はサーバーが毎回期限を確かめるので、ログインできる期間は7日のまま変わらない（要件定義書のとおり）。
- サーバー（`get_current_user`）は、届いたものに応じてエラーコードを分ける。

| 届いたもの | 返すもの | 画面 |
| --- | --- | --- |
| Cookie なし | 401 `UNAUTHENTICATED` | お知らせなし |
| 期限切れの JWT（PyJWT の `ExpiredSignatureError`） | 401 `TOKEN_EXPIRED` | ログイン画面の上に「ログインの有効期限が切れました。もう一度ログインしてください。」 |
| トークンのバージョンが古い JWT（パスワード変更で無効） | 401 `TOKEN_REVOKED` | ログイン画面の上に「パスワードが変更されたため、もう一度ログインしてください。」 |
| 署名が正しくない・壊れた JWT | 401 `UNAUTHENTICATED` | お知らせなし |

- `TOKEN_EXPIRED`・`TOKEN_REVOKED`・壊れた JWT を返すときは、同時に Cookie を削除する（`delete_cookie`）。お知らせは1回だけ出て、次からはふつうの未ログインとして扱われる。
- 画面側に「ログインしたことがある」印を残す方式は使わない。理由：判断をサーバーにまとめて pytest で確かめられるようにするため。ブラウザの保存場所は利用者の操作で消えることがあるため。期限切れとパスワード変更を区別できないため。
- テスト：Cookie なし・期限切れ・バージョンが古い・署名が不正のそれぞれで、正しいエラーコードが返り、必要な場合に Cookie を削除する Set-Cookie が返ること。

### 3-4. ログイン中に、ウェルカム・ログイン・新規登録を開いた場合

- どれも本棚へ移す（ブラウザの履歴は置き換え、戻るで元の画面に戻らないようにする）。理由：ログイン中の人にはすることがないため。別のアカウントにしたい場合はプロフィールからログアウトする（MVP でアカウントの切り替えは作らない）。
- サーバーは止めない。ログイン中に `POST /auth/login` が来ても、ふつうにログインの処理をし、新しい JWT で Cookie を上書きする（期限はその時点から7日になる）。理由：止める安全上の理由がなく、止めると「Cookie は残っているが無効」のような中途半端な状態の人がログインし直せなくなるおそれがあるため。

### 3-5. ログイン後の戻り先

- ログインが必要な画面から未ログインでログイン画面へ移すときは、開こうとしていた画面のパスを `?next=` で付ける（例：`/login?next=/insights/3f2a…`）。ログインに成功したら、`next` を確かめてそこへ移す。
- `next` はアプリの中のパス（`/` で始まり `//` で始まらないもの）だけを受け付ける。`/login`・`/register`、外部のサイト、値なしの場合は本棚へ移す。理由：外部のサイトへ移されるのを防ぐため（オープンリダイレクト対策）。ログイン画面へ戻ってきて回り続けるのを防ぐため。
- ログインの API は移り先を返さず、確かめは画面で行う（サーバーの認証・認可には関係しないため）。
- ログイン画面と新規登録画面を行き来するときは、`next` を付けたまま持ち回る（新規登録へ移ってからログインに戻ったときに、元の画面へ戻れるようにするため）。新規登録が成功したら `next` は使わず本棚へ移す（新しいアカウントには本も気づきもなく、前の画面へ戻っても「見つかりませんでした」になるだけのため）。入力したメールアドレスなどは URL に載せず、持ち回らない（履歴やログに残るため）。
- ログイン後に利用規約・プライバシーポリシーを見る場所は、プロフィールの「その他」（screens.md「9.」のとおり）。
- 戻り先が回答前の AI提案の場合は、決め済みのとおり「このAI提案は終了しました」が表示される。書いていた文を失わない方法は 3-6 のとおり。

### 3-6. 書いている途中でログインの期限が切れた場合

見本：[mockups/relogin.html](mockups/relogin.html)

- 文を書く画面（気づきの作成・編集、AI提案の回答・送り直し）で、保存・送信に 401（`TOKEN_EXPIRED`・`TOKEN_REVOKED`）が返った場合は、ログイン画面へ移らず、その場で下からログインのシートを出す。書いた文は画面に残したまま。
  - 見出し：期限切れは「ログインの有効期限が切れました」、パスワード変更で無効は「パスワードが変更されたため、もう一度ログインしてください」。どちらも「書いた内容はこの画面に残っています。ログインすると、そのまま保存します。」を添える。
  - ボタン：「ログインして保存する」（AI提案では「ログインして送る」）、「キャンセル」。
- ログインに成功したら（新しい JWT が Cookie に入る）、押そうとしていた保存・送信を自動で1回送り直す。成功したら、ふだんと同じ動き（気づきの詳細へ移る、など）。
- 理由：
  - ログイン画面へ移ると書いた文が消えるため。
  - AI提案の画面は、回答を送る前に離れると AI提案が削除され回数も戻らない決まりのため、ログイン画面へ移ること自体が損になるため。
  - 書きかけをブラウザの保存場所に入れる方式は、個人的な気づきが共有のパソコンに残るおそれがあり、「下書きは作らない」決まりとも紛らわしいため使わない。
- 別のアカウントでログインした場合は、その人の本・気づき・AI提案ではないので 404 になる（認可のとおり）。そのときは「見つかりませんでした」と出し、書いた文は画面に残す。
- 「キャンセル」ではシートを閉じ、書いた文は残す（保存はされていない）。
- 画面を再読み込みした場合は文が消える（守るのは、保存・送信を押した時点で期限切れだった場合）。
- ログインはふだんと同じ `POST /auth/login`・同じ回数制限を使う。サーバー側の追加はない。
- 作り方：「401 が返ったらログインのシートを出し、成功したら同じリクエストを送り直す」部品を1つ作り、文を書く画面で使う。

## 4. Google Books

### 4-1. タイトル・著者が上限を超える本

- 検索結果から追加する本のタイトル（200文字）・著者（100文字）が上限を超える場合は、追加を断らず、切り詰めて保存する。
  - タイトル：199文字で切り、「…」を付けて200文字にする。
  - 著者：著者の名前の区切りで切り、入りきらない分は「ほか」にする（例：`山田太郎、佐藤花子、鈴木一郎 ほか`）。1人目だけで100文字を超える場合は、99文字で切って「…」を付ける。
  - 文字数は見た目の1文字を1文字と数え、絵文字などの途中で切らない（書記素クラスタで数える）。
- 理由：Google Books から追加した本は編集できないため、断ると利用者はその本で気づきを書けなくなるため。上限を1種類にそろえると、データベース・画面・AI に送る内容の長さがそろうため。画面のタイトルはもともと2行までしか出さないため、切れても見た目はほぼ変わらない。第3段階で同じ本を探すときは識別子・ISBN を使うので影響しない。

### 4-2. API キー

- Google Books の公開データの検索にも、アプリを識別する API キーが必要。
- `.env` の `GOOGLE_BOOKS_API_KEY` に置き、`pydantic-settings` で起動時に読み込む（なければ起動を止める）。`.env` は `.gitignore` に入れ、中身を空にした `.env.example` を GitHub に上げる。OpenAI の API キーも同じ扱い。
- 開発用と本番用の2つのキーに分ける。どちらも「Books API だけに使える」制限を付け、本番用は「EC2 の IP アドレスからだけ使える」制限も付ける（EC2 は Elastic IP で IP を固定する）。
- キーは URL の `?key=` ではなく、`X-goog-api-key` ヘッダーで送る（通信のログやエラーの記録に URL ごとキーが残らないようにするため）。
- テストでは Google Books を偽物に置き換えるため、GitHub Actions にキーは要らない。

### 4-3. Google の表記（Branding Guidelines）

見本：[mockups/brand.html](mockups/brand.html)

- 検索結果のすぐ近く（「検索結果」の右）に「Powered by Google」のロゴを1つだけ置く。ロゴは Google が配っている画像をそのまま使い、欠けさせたり重ねたりしない。
- 検索結果の本ごとに「Google Books で見る」のリンクを付け、新しいタブで Google Books の本のページ（`volumeInfo.infoLink`）を開く（`target="_blank"`・`rel="noopener noreferrer"`）。検索結果の API は本ごとにこの URL も返す。
  - 世界観を崩さないよう、補足の文字と同じ色・最小の文字の大きさ（12px）で小さく出す。
  - 追加の確認のシートと本の詳細には置かない（決まりで求められているのは検索結果だけのため）。
- 検索結果は Google Books が返した順のまま出し、中身を書き換えない（「本棚にあります」の目印を付けるのは並べ替えではないので問題ない）。
- プレビュー（試し読み）は出さないので、プレビューの決まりは関係しない。
- ロゴと表記は、visual.md の「見た目は独自にする」方針の例外とする。

### 4-4. Google の情報の保存

- Google の API の利用規約には、内容の持ち主か法律が許していない限り、API の内容でデータベースを作ったり永続的なコピーを作ったりしない、キャッシュの決まりより長く保存しない、という禁止事項がある。
- そのため、保存するのは利用者が自分の本棚に入れた本の最小限の書誌情報だけにする（Google Books の識別子・タイトル・著者・ISBN・表紙の URL）。
  - 表紙は画像を保存せず、URL だけを保存して表示のたびに読み込む。
  - 説明文・評価・ページ数・プレビューなど、使わない項目は取らない・保存しない。
  - 検索結果は保存しない（検索のたびに Google Books に問い合わせる）。
- 規約の解釈には幅があり、完全に安全とは言い切れない（要件定義書の既知の制限に記載）。問題になった場合は、識別子だけを保存し表示のたびに取り直す形に変える（そのときは、本を削除しても気づきに残す本のタイトルのコピーの扱いを見直す）。

### 4-5. 利用枠を超えたとき

- Google Books の利用枠（初期設定で1日およそ1000回。実際の値は Google Cloud の管理画面で確認する）を超えて 429 が返った場合、サーバーは 503 `BOOK_SEARCH_LIMIT` を返す。ふつうの失敗（障害・時間切れ）は 502 `BOOK_SEARCH_FAILED`。
  - 理由：利用枠切れと障害を、ログで見分けられるようにするため。
- 画面：「本の検索が混み合っています。時間をおいてお試しいただくか、手入力で追加してください。」と「手入力で追加する」ボタン。
  - 「明日0時」とは書かない。理由：Google の利用枠が戻る時刻は日本時間の0時ではないため。
  - 理由（手入力の案内）：検索できなくても、手入力なら本を追加して気づきを書き始められるため。
- 検索結果から追加するとき（サーバーが Google Books から取り直すとき）に利用枠切れになった場合も同じ文を出し、追加の確認のシートは閉じずに残す（押した本を見失わないため）。
- 利用枠切れはログに重要度「エラー」で残す（ふつうは起きないので、起きたら作る側が気づいて利用枠の引き上げなどを検討するため）。
- 利用枠切れの間に手入力で追加した本は、後で同じ本を検索から追加すると重複しうるが、要件定義書の既知の制限（手入力の本は重複を判定しない）と同じ扱いとする。

## 5. 入力の確かめ方と回数制限

### 5-1. 文字数の数え方

- 画面もサーバーも「見た目の1文字」（書記素クラスタ）で数える（要件定義書のとおり）。画面は `Intl.Segmenter`、サーバーは `grapheme` などのライブラリを使う。
  - 理由：JavaScript の `.length` と Python の `len()` は数え方が違い、絵文字（例：`😀` は画面で2・サーバーで1、家族の絵文字は画面で8・サーバーで5）や、分かれた形の濁点（「か＋゛」）で見た目の文字数と合わないため。

| 入力 | 見た目 | JavaScript の `.length` | Python の `len()` |
| --- | --- | --- | --- |
| `気づき` | 3 | 3 | 3 |
| `😀` | 1 | 2 | 1 |
| `👨‍👩‍👧` | 1 | 8 | 5 |
| `が`（か＋゛） | 1 | 2 | 2 |

- サーバーは、前後の空白を除いたあと Unicode の NFC に正規化してから数え、その形で保存する。理由：Mac からコピーした分かれた形の濁点を1文字にそろえるため。保存する形がそろい、第2段階の検索でも形の違いで見つからないことがないため。
- 判定はサーバーが正。画面の文字数は目安の表示（画面は書き換えられるため）。
- 見た目の文字数とは別に、サーバーで中身の量（コードポイントの数）の上限も確かめる。見た目の上限の4倍まで。理由：見た目1文字に記号を大量に重ねる書き方（Zalgo テキスト）で、見た目は上限内でも中身がとても大きいデータを送れてしまうため。ふつうの日本語や絵文字では届かない。
- Caddy で、1回のリクエストの大きさに上限（1MB）を付ける。理由：巨大なデータを入口で止めるため。SHIORIME の入力で一番大きい気づき（1000文字×4倍・UTF-8 で1文字最大4バイト）でも約16KB なので、十分な余裕がある。
- 数え方は関数1つにまとめ、気づき・引用・回答・タイトル・著者、Google Books の切り詰め（4-1）のすべてで使う。Pydantic の `AfterValidator` で、空白の除去・正規化・文字数の確認をまとめて行う。
- データベースでは見た目の文字数の上限をかけず、中身の量の上限（見た目の上限の4倍）に合わせる（database.md で書く）。理由：PostgreSQL の `VARCHAR(n)` はコードポイントで数えるため、見た目の上限でかけると家族の絵文字などで入らなくなるため。
- テスト：上の表の文字や、ちょうど上限・1つ超え・前後の空白・空白だけ・分かれた形の濁点・記号を大量に重ねた文字列を、サーバーのテストで確かめる。画面（MVP ではフロントのテストは書かない）は、同じ例を手で確かめる一覧にする。

### 5-2. 回数制限（ログイン・新規登録・本の検索・パスワードの再確認）

| 対象 | 上限（要件定義書・screens.md） | 数えるもの | 単位 |
| --- | --- | --- | --- |
| ログイン | 1分に5回 | 失敗だけ | 接続元の IP |
| 新規登録 | 1時間に5件 | 登録できた分と「既に登録されています」（入力の誤り 422 は数えない） | 接続元の IP |
| 本の検索 | 1分に10回 | 検索のリクエスト | 利用者 |
| パスワードの再確認（パスワードの変更・退会） | 1時間に5回 | 失敗だけ（変更と退会を合わせて数える） | 利用者 |

- 数え方は、今から遡った時間の中の回数で数える（スライディングウィンドウ）。
- ログインで成功を数えない理由：同じネットワークを使う家族などが、ふつうにログインしただけで制限にかかりやすくなるため。総当たりは失敗の連続なので、失敗だけで十分に止められる。
- ログインは、直近1分の失敗が5回に達していたら、パスワードを確かめる前に断る。理由：確かめてから断ると総当たりの役に立ってしまうため。重い計算（Argon2id）をさせられてサーバーが重くなるのも防ぐため。
- 存在しないメールアドレスでも、ダミーのハッシュで同じ計算をして、返事の速さをそろえる。理由：返事の速さの違いで登録済みかを知られないようにするため（タイミング攻撃対策。要件定義書の「どちらが誤りか伝えない」を時間の面でも守る）。
- 新規登録で「既に登録されています」を数える理由：要件定義書の既知の制限のとおり登録済みかがわかってしまうため、他人のメールアドレスを次々に試す速さを1時間5件に抑えるため。入力の誤りを数えない理由：利用者の打ち間違いで制限を使わせないため（アカウントも作られず、情報も漏れない）。
- 記録は PostgreSQL の表に「何の制限か・誰（IP または利用者）・いつ」だけを残す。理由：FastAPI のメモリに持つと再起動で消え、複数動かすと別々に数えてしまうため。Redis はコンテナが増えるため、MVP では使わない（利用者が増えて重くなったら置き換える）。
- 接続元の IP は個人に関わる情報なので、記録は1日で消す（2-8 の片付けのコンテナで消す）。プライバシーポリシーにも書く。
- 接続元の IP は、Caddy から渡される `X-Forwarded-For` だけを信頼して取り出す（notes.md 3章のとおり）。
- 断るときは 429 と、何秒後に試せるかを `Retry-After` ヘッダーで返す。エラーコードは `LOGIN_RATE_LIMIT`・`REGISTER_RATE_LIMIT`・`SEARCH_RATE_LIMIT`・`PASSWORD_CONFIRM_RATE_LIMIT`。画面の文言は screens.md のとおり。
- パスワードの再確認の制限を付ける理由：ログインした後の画面なのでログインの回数制限が効かず、共有のパソコンでログインしたまま離れた場合や、JWT を盗まれた場合に、今のパスワードを何回でも試され、当たったらパスワードを変えて本人を締め出す（アカウント乗っ取り）ことができてしまうため。
  - 利用者ごとに数える理由：ログイン後なので誰の操作かがわかり、ネットワークを変えてもすり抜けられないため。
  - 変更と退会を合わせて数える理由：どちらからでも試せるため、別々に数えると上限が2倍になるため。
  - 1時間に5回の理由：本人がパスワードを変える・退会するのはまれで、1時間に5回打ち間違えることはほぼないため。1日に試せる回数が最大120回になり、総当たりはほぼできないため。
  - ログインと同じく、上限に達していたらパスワードを確かめる前に断る。エラーコードは `PASSWORD_CONFIRM_RATE_LIMIT`。画面は欄の下に「パスワードの入力の失敗が続いたため、しばらく操作できません。1時間ほど待ってからお試しください。」
  - 上限に達しても全端末からログアウトさせない（わざと失敗して本人をログアウトさせる嫌がらせに使われるため）。上限に達したことはログに重要度「警告」で残す。
  - 本人がパスワードを忘れた場合は、もともと変更できない（パスワードの再設定は第2段階。要件定義書の既知の制限）ので、この制限で新しく困ることはほぼない。
- 回数制限の部品は1つにまとめ、4つの制限で使い回す。
- アカウントごとのロックは MVP では入れない。理由：他人がわざと失敗してそのアカウントをロックできてしまうため。たくさんの接続元から同じアカウントを狙われると接続元ごとの制限では止めきれないことは既知の制限とし、第2段階の候補とする。
- テスト：5回目は通り6回目で断られること（ログインは失敗で数える）、成功は数えないこと、1分たつと戻ること（時刻を差し替える）、新規登録で 422 は数えず「既に登録されています」は数えること、存在しないメールアドレスでもパスワードの計算をすること。

## 7. エンドポイントの詳細

### 7-1. 認証

#### 新規登録 `POST /api/v1/auth/register`

| 項目 | 内容 |
| --- | --- |
| 認証 | 不要 |
| 受け取るもの | `email`（254文字まで・メールアドレスの形）、`password`（前後の空白を除いて8〜128文字）、`attribute`（下の5つの記号のどれか）、`agreed_to_terms`（`true` だけ受け付ける） |
| サーバーですること | 回数制限を確かめる → メールアドレスは前後の空白を除いて小文字にそろえる → 同じメールアドレスがないか確かめる → パスワードを Argon2id でハッシュ化 → ユーザーを作る → JWT を Cookie に入れる |
| 成功 | 201、Cookie（`access_token`。属性はログインと同じ）、`{"id", "email", "attribute"}` |
| 回数制限 | 接続元ごとに1時間5件（登録できた分と「既に登録されています」を数える。5-2） |

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 入力の誤り（形・長さ・未選択・同意していない） | 422 | `VALIDATION_ERROR`（項目ごとの理由は `error.fields`） |
| 登録済み | 409 | `EMAIL_ALREADY_REGISTERED` |
| 回数制限 | 429 | `REGISTER_RATE_LIMIT` |

- 登録が成功したら、そのままログイン状態にする（JWT を Cookie で返す）。理由：screens.md のとおり登録後は本棚へ移るため、もう一度メールアドレスとパスワードを入力させないため。画面がもう一度ログインの API を呼ぶ形にすると、通信が2回になり、その間の失敗（登録はできたがログインに失敗）の扱いが増えるため。

属性の記号

| 画面の表示 | 記号 |
| --- | --- |
| 高校生 | `high_school` |
| 大学生・専門学生 | `university` |
| 社会人 | `working` |
| 主婦・主夫 | `homemaker` |
| その他 | `other` |

- 属性を記号で送る理由：表示名を変えても、画面を直すだけで保存した値を直さなくてよいため。日本語のままだと「・」の全角・半角などの違いで別の値になるため。Pydantic でこの5つ以外は受け付けない（422）。
- AI に送るときは、サーバーで日本語に直してから送る（AI が読みやすいようにするため）。

#### ログイン `POST /api/v1/auth/login`

| 項目 | 内容 |
| --- | --- |
| 認証 | 不要（ログイン中でも受け付け、新しい JWT で上書きする。3-4） |
| 受け取るもの | `email`、`password`（前後の空白を除く） |
| サーバーですること | 回数制限を先に確かめる → メールアドレスでユーザーを探す（ないときもダミーのハッシュで同じ計算をする） → パスワードを確かめる → JWT を Cookie に入れる |
| 成功 | 200、Cookie、`{"id", "email", "attribute"}` |
| 回数制限 | 接続元ごとに失敗を1分5回（5-2） |

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 入力の誤り（空欄など） | 422 | `VALIDATION_ERROR` |
| メールアドレスかパスワードが違う | 401 | `INVALID_CREDENTIALS` |
| 回数制限 | 429 | `LOGIN_RATE_LIMIT` |

- 返事に自分の情報（ID・メールアドレス・属性）を入れる。理由：ログイン直後に画面がもう一度 `GET /me` を呼ばなくて済むため。新規登録・`GET /me` と同じ形にそろえ、画面の処理を1つにするため。
- JWT は本文に入れない（Cookie だけ）。本文に入れると画面の JavaScript から読めてしまい、HttpOnly にした意味がなくなるため。本日の残り回数も入れない（ログインの役割を「誰か」を返すことだけにするため）。

#### ログアウト `POST /api/v1/auth/logout`

| 項目 | 内容 |
| --- | --- |
| 認証 | 不要 |
| サーバーですること | Cookie を削除する（発行時と同じ属性で、`Max-Age=0`） |
| 成功 | 204 |

- ログインしていなくても（Cookie がない・期限切れ）、いつでも 204 を返す。理由：期限切れの状態で押した場合や、返事が届かずもう一度押した場合にエラーを見せず、何度押しても「ログアウトした状態」になるようにするため（冪等）。
- GET にしない理由：状態を変える操作は GET で作らない決まりのため（別のサイトのリンクから勝手にログアウトさせられないように）。
- ログアウトは Cookie を消すだけで、サーバー側で JWT を無効にはしない（盗まれた JWT が期限まで使えることは既知の制限。第2段階のリフレッシュトークン導入時に見直す）。

### 7-2. 自分

#### 自分の情報 `GET /api/v1/me`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要（`get_current_user`） |
| 成功 | 200、`{"id", "email", "attribute"}`（ログイン・新規登録の返事と同じ形） |
| エラー | 401（`UNAUTHENTICATED`・`TOKEN_EXPIRED`・`TOKEN_REVOKED`。3-3） |

- 画面は、SHIORIME が開かれたとき（URL を開いた・再読み込みした・ブックマークから開いた）に1回だけ呼び、ログイン中かどうかでどの画面へ案内するかを決める（3-2）。アプリの中で画面を移るときは呼ばず、最初に取った情報を覚えて使う（プロフィールのメールアドレス・属性の表示にも使う）。途中でほかの API が 401 を返したら、ログインが切れたとして扱う（3-6）。
- `get_current_user` との違い：`get_current_user` は、ログインが必要なすべての API が `Depends` で使う関数（Cookie の JWT を確かめてログイン中のユーザーを取り出す＝認証）。`GET /me` は、それを使って自分の情報を返すだけの API。
- 返さないもの：パスワードのハッシュ、トークンのバージョン番号、JWT そのもの、本日の残り回数（下の `GET /me/ai-usage` に分ける）。

#### 本日の AI提案の残り回数 `GET /api/v1/me/ai-usage`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | その人の止まった AI提案を先に片付ける（2-8） → 本日（日本時間）の個人の回数とアプリ全体の回数を数える |
| 成功 | 200、`{"remaining_today": 3, "daily_limit": 5, "app_limit_reached": false}` |

- プロフィール画面を開くたびに呼ぶ（気づきの詳細は、気づきの取得の返事に残り回数を入れる。screens.md「6.」）。
- `GET /me` と分ける理由：`GET /me` をログイン・新規登録の返事と同じ形にそろえるため。残り回数は AI提案を使うたびに変わるので、アプリを開いたときに1回だけ取る `GET /me` に入れると古い値のまま表示されやすく、プロフィールを開くたびに取り直したいため。将来「今月使った回数」などを足しても `GET /me` が重くならないため。

#### 属性の変更 `PATCH /api/v1/me`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `attribute`（5つの記号のどれか）だけ。ほかの項目（`email` など）を送られたら 422（Pydantic の `extra="forbid"`） |
| 成功 | 200、`{"id", "email", "attribute"}`（`GET /me` と同じ形。画面は覚えている自分の情報をこれで更新する） |
| エラー | 422 `VALIDATION_ERROR` |

- PATCH（一部だけ変える）にする理由：変えられるのは属性だけで、メールアドレスは変えられない決まりのため。PUT（全部を送って置き換える）だと、変えられないメールアドレスも送ることになり紛らわしいため。将来変えられる項目が増えても、同じ `PATCH /me` に項目を足すだけで済むため。
- 属性は Python の `StrEnum` で1か所に定義し、入力の確認・保存・AI に送るときの日本語への変換で同じものを使う。

#### パスワードの変更 `POST /api/v1/me/password`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `current_password`、`new_password`（どちらも前後の空白を除く。新しい方は8〜128文字） |
| サーバーですること | ① 回数制限を確かめる ② 今のパスワードを確かめる（違えば失敗として数える） ③ 新しいパスワードが今と同じでないか確かめる ④ 新しいパスワードを Argon2id でハッシュ化して保存 ⑤ トークンのバージョン番号を1つ上げる（今までの JWT がすべて使えなくなる＝全端末でログアウト） ⑥ この端末の Cookie も消す |
| 成功 | 204。画面はログイン画面へ移り「パスワードを変更しました。新しいパスワードでログインしてください。」 |
| 回数制限 | パスワードの再確認：退会と合わせて、利用者ごとに失敗を1時間5回（5-2） |

| エラー | ステータス | エラーコード | 画面（欄の下） |
| --- | --- | --- | --- |
| 新しいパスワードの長さが範囲外など | 422 | `VALIDATION_ERROR` | 「8〜128文字で入力してください」 |
| 今のパスワードが違う | 400 | `CURRENT_PASSWORD_INCORRECT` | 「今のパスワードが正しくありません」 |
| 新しいパスワードが今と同じ | 400 | `SAME_AS_CURRENT_PASSWORD` | 「今と同じパスワードは使えません」 |
| 回数制限 | 429 | `PASSWORD_CONFIRM_RATE_LIMIT` | 5-2 の文 |

- POST にする理由：呼ぶたびにトークンのバージョン番号が上がり、結果が変わるため（何度呼んでも同じになる PUT の性質に合わない）。
- 今のパスワードが違うときに 401 にしない理由：画面は 401 を「ログインが切れた」と判断してログインのシートを出すため（3-6）。打ち間違いなのに「ログインし直してください」が出ないようにする。
- 新しいパスワードが今と同じなら断る。理由：「変更」を押したのに何も変わらないのは不自然なため。今のパスワードが正しいとわかった後にだけ判定する（先に判定すると、今のパスワードのヒントを与えてしまうため）。比べるのは、送られた `current_password` と `new_password`（前後の空白を除いた後）。本人であることは確かめ済みなので、回数制限には数えない。
- 断ることで「今のパスワードのまま他の端末からログアウトさせる」方法はなくなるが、新しいパスワードに変えれば全端末からログアウトできる。全端末からのログアウトの専用ボタンは第2段階の候補とする。

#### 退会 `POST /api/v1/me/withdraw`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `password`（前後の空白を除く） |
| サーバーですること | ① 回数制限を確かめる ② パスワードを確かめる（違えば失敗として数える） ③ ユーザーを削除する（本・気づき・AI提案・個人の AI 利用回数はデータベースの決まり（CASCADE）でまとめて消える。アプリ全体の利用回数は減らさない） ④ この端末の Cookie を消す |
| 成功 | 204。画面はログイン画面へ移り「退会しました。ご利用ありがとうございました。」 |
| 回数制限 | パスワードの再確認：パスワードの変更と合わせて、利用者ごとに失敗を1時間5回（5-2） |

| エラー | ステータス | エラーコード | 画面（欄の下） |
| --- | --- | --- | --- |
| パスワードが空 | 422 | `VALIDATION_ERROR` | 「パスワードを入力してください」 |
| パスワードが違う | 400 | `PASSWORD_INCORRECT` | 「パスワードが正しくありません」 |
| 回数制限 | 429 | `PASSWORD_CONFIRM_RATE_LIMIT` | 5-2 の文 |

- `DELETE /me` にしない理由：DELETE に本文（パスワード）を付けるのは HTTP の決まりで意味が定められておらず、途中の機械や一部の道具で本文が捨てられることがあるため。パスワードを URL に付けるとログや履歴に残るため。パスワードを本文で確実に送ることを優先し、パスワードの変更（`POST /me/password`）と形をそろえた。
- 他の端末の JWT は、次に使われたときに `get_current_user` の「ユーザーが存在しない」で断られる。
- AI提案の作成中に退会した場合、裏の処理は AI提案が消えていれば結果を保存しない（notes.md 4章のとおり）。

### 7-3. 本

#### 本棚の一覧 `GET /api/v1/books`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの（クエリパラメーター・どれも任意） | `status`（`reading`／`finished`。付けなければすべて）、`cursor`（続きの位置） |
| サーバーですること | 自分の本だけを対象にし（認可）、`status` があれば絞り込む → 冊数を数える → 登録した日時が新しい順に30冊（＋続きがあるかを知るために1冊多く）取る |
| 成功 | 200、下の形 |
| エラー | 422 `VALIDATION_ERROR`（`status` が決まった値以外・`cursor` が壊れている） |

```json
{
  "items": [
    { "id": "3f2a…", "title": "嫌われる勇気", "cover_url": "https://…", "status": "reading" }
  ],
  "total": 40,
  "next_cursor": "…（続きがなければ null）"
}
```

- 読書ステータスはクエリパラメーターで受け取る。理由：パス（`/books/reading`）は「何を取るか」を表す場所で、`reading` という ID の本とも読めてしまうため。絞り込みの条件はクエリに入れるのがふつうで、第2段階で「タイトルで探す」を足すときも `?status=reading&q=…` と並べるだけで済むため。
- 「すべて」は `status` を付けない形にする。理由：読書ステータスを将来足しても「すべて」の意味が自動で「全部」のまま保てるため。両方の値を並べて送る形は、ステータスを足したときに画面の送り方も直さないと、新しいステータスの本が「すべて」に出なくなるため。
- 絞り込みのあり・なしで API を分けない（1つの API で、`status` が付いていれば絞り込む）。理由：どれも同じ「自分の本の一覧」で、返す形も同じため。分けるとほぼ同じコードが2つになり、片方だけ直し忘れる原因になるため。
- 読書ステータスは Python の `StrEnum`（`reading`・`finished`）で定義する（属性と同じ考え方）。
- 冊数（`total`）は、同じ返事に入れ、続きを読み込むとき（2回目以降）も毎回数え直して返す。理由：1回目と2回目の間に別の端末で本を追加・削除した場合も冊数が正しくなるため。返事の形が1回目と2回目で同じになり、画面の処理が1つで済むため。
  - 冊数はデータベースで数え（`COUNT(*)`）、30冊もデータベースで絞る（`LIMIT`）。理由：全部の本をサーバーに取ってきてから Python で数えて切ると、本が多いほど遅くなるため。
  - 「利用者＋読書ステータス」のインデックスを付けて、数えるのを速くする（database.md）。
  - 既に画面に並んでいる一覧には、別の端末で追加した本は出てこない（一覧を開き直すと出る）。カーソルで続きを読むため、同じ本が2回出たり飛ばされたりはしない。
- 1冊ずつに返すのは、画面に表示するもの（表紙の URL・タイトル・読書ステータス）と、本の詳細へ移るための `id` だけ。理由：一覧の API は、その画面に必要な最小限にするため。著者・ISBN・登録した日時などは本棚に表示しないので返さない（登録した日時は並び順に使うだけで、並べるのはサーバー）。
- 表紙の URL がない本は `cover_url` を `null` で返し、画面がアイコン画像を出す。
- 項目名は `book_id` ではなく `id`。理由：本の一覧の中の1冊なので「本の」を言わなくても伝わるため。気づきの中で「どの本の気づきか」を表すときは、気づき自身の `id` と区別するため `book_id` と書く。

#### 本の検索（Google Books） `GET /api/v1/catalog/search`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの（クエリパラメーター） | `q`（検索の言葉。必須。前後の空白を除いて空なら 422）、`offset`（何件目から。任意。付けなければ0） |
| サーバーですること | ① 回数制限（1人1分10回）を確かめる ② API キーを付けて Google Books に21件（続きがあるかを知るために1件多く）を頼む ③ 表紙の URL を https に直し、タイトル・著者を整える ④ 20冊分の `google_volume_id` をまとめて1回でデータベースに聞き、自分の本棚にある本の ID を付ける |
| 成功 | 200、下の形 |

```json
{
  "items": [
    {
      "google_volume_id": "abc123",
      "title": "嫌われる勇気",
      "authors": "岸見一郎、古賀史健",
      "published_year": 2013,
      "cover_url": "https://…",
      "info_link": "https://books.google.com/…",
      "shelf_book_id": "3f2a…（本棚になければ null）"
    }
  ],
  "next_offset": 20
}
```

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 検索の言葉が空など | 422 | `VALIDATION_ERROR` |
| 回数制限 | 429 | `SEARCH_RATE_LIMIT` |
| Google Books の利用枠切れ | 503 | `BOOK_SEARCH_LIMIT`（4-5） |
| Google Books の障害・時間切れ | 502 | `BOOK_SEARCH_FAILED` |

- URL を `/books` の下ではなく `/catalog` に置く理由：`/books` の下はすべて「自分の本棚の本」を返すのに、検索で返すのは「まだ本棚に入っていない Google Books の本」で、別のものだから。第2段階の「本棚の中を探す」（`GET /books?q=…`）と見た目が似て取り違えるのを防ぐため。`/books/search` だと `/books/{book_id}` より先に定義する必要がある（FastAPI は上から URL の形で照らし合わせ、`/books/{book_id}` が先だと `search` を本の ID として扱い 422 になる）が、`/catalog` ならその注意も要らない。
- URL は画面ではなくデータのまとまり（リソース）で作る。本の検索・登録の画面は `GET /catalog/search` と `POST /books` の2つを使う。
- 続きは「何件目から」（`offset`）で受け取る。理由：Google Books が「何件目から」（`startIndex`）の数字でしか受け付けないため。本棚の一覧でカーソルを使った理由（途中の追加・削除で同じ本が2回出たり飛ばされたりする）は、利用者が「もっと見る」を押す数秒の間に検索結果が変わることはほぼないので、ここでは問題になりにくい。
- `next_offset` を返し、続きがなければ `null`。理由：本棚の一覧の `next_cursor` と同じく「`null` なら続きなし」と画面の判断をそろえるため。続きがあるかは、21件目があるかで判断する（Google Books が返す総件数は目安で正確ではないため）。
- 1冊ずつに返すのは、画面に表示するもの（表紙・タイトル・著者・出版年・「Google Books で見る」のリンク）と、表示しないが押したときに使う `google_volume_id`（本棚に追加するとき）、`shelf_book_id`（本棚にある本の詳細へ移るとき）。
- `shelf_book_id` は、本棚にあれば自分のデータベースの本の ID、なければ `null`。「あるか」と「ID」の2つの項目にしない理由：「あるのに ID が null」のようなありえない組み合わせを作らないため。画面は `shelf_book_id` があれば「本棚にあります」を出して `/books/{shelf_book_id}` へ、なければ追加のシートを出す。
- 本棚にあるかは、20冊分の `google_volume_id` をまとめて1回で聞く（`IN` 句）。1冊ずつ聞くと問い合わせが20回になる（N＋1問題）ため。自分の本だけを対象にする（認可）。

#### 本棚に追加（検索結果から） `POST /api/v1/books/from-catalog`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `google_volume_id`、`status`（`reading`／`finished`）の2つだけ。ほかの項目（`title` など）を送られたら 422（`extra="forbid"`） |
| サーバーですること | ① 自分の本棚に同じ `google_volume_id` の本がないか確かめる（あれば 409） ② Google Books から `google_volume_id` で情報（タイトル・著者・表紙・ISBN）を取り直し、タイトル・著者を切り詰め（4-1）、表紙の URL を https に直す ③ 保存する |
| 成功 | 201、`Location: /api/v1/books/{本の ID}`、`{"id": "…"}` |

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 入力の誤り | 422 | `VALIDATION_ERROR` |
| 同じ本が本棚にある | 409 | `BOOK_ALREADY_ON_SHELF`（`error.details.book_id` に本棚にある本の ID） |
| Google Books にその本がない（でたらめな番号） | 404 | `CATALOG_BOOK_NOT_FOUND` |
| Google Books の利用枠切れ | 503 | `BOOK_SEARCH_LIMIT` |
| Google Books の障害・時間切れ | 502 | `BOOK_SEARCH_FAILED` |

- URL：本を1冊作る操作なので POST。URL に動詞（register など）は入れない（メソッドが「何をするか」、URL が「何に対してか」を表すため）。まとまりの名前は複数形（`/books`）にそろえる。増えるのは自分の本棚なので `/books` のまとまりに置き、作り方の違い（Google Books の目録から）を `from-catalog` で表す。`POST /catalog` にしない理由：「世の中の本の目録に1冊増やす」と読めてしまうため。`/books/{book_id}` より先に定義する。
- 手入力と API を分ける理由：受け取るもの（`google_volume_id`／タイトル・著者）も、サーバーですること（Google Books から取り直す／入力のまま保存）も違い、役割（責務）が違うため。1つにまとめて `source` で送り分ける形（判別共用体）より、確かめ方が単純で、テストも分けて書ける。
- 受け取るものを `google_volume_id` と `status` だけにする理由：タイトル・著者・表紙・ISBN は、改ざんを防ぐためサーバーが Google Books から取り直すので、画面から送ってもらう必要がないため。読書ステータスだけは利用者が選んだもので、Google Books からは手に入らないため。決めた項目以外を断るのは、送ればタイトルを変えられると誤解された作りのまま、将来うっかりその値を使うコードを書くのを防ぐため。
- 重複したときに本棚にある本の ID を返す理由：要件定義書のとおり、画面が「この本は既に本棚にあります」と出して本の詳細へ案内するため。エラーの形に `details` を足し、画面が次の行動に必要な情報を受け取れるようにする。
- 処理の順番を「本棚にあるか確かめる → Google Books → 保存」にする理由：本棚にすでにあれば Google Books に聞く必要がないため。データベースは速く失敗しにくく、Google Books はインターネットの向こうで遅く失敗しうるので、速いほうを先にしてだめならすぐ終える（早期リターン）。Google Books の利用枠もむだに使わない。
- 確かめてから保存するまでの間（Google Books に聞いている約1秒）に、別の端末で同じ本が追加されると、どちらも「ない」と確かめて2冊保存されうる（TOCTOU）。これを防ぐため、データベースに「`user_id` と `google_volume_id` の組み合わせは1つまで」の決まり（複合ユニーク制約）を付ける（database.md）。保存で引っかかったら（`IntegrityError`）、本棚にある本の ID を取り直して 409 `BOOK_ALREADY_ON_SHELF` を返す。新しい列は要らない。受付番号（冪等キー）は同じ依頼の重複を防ぐもので、別々の端末からの別々の依頼は防げないため使わない。手入力の本は `google_volume_id` が `NULL` で、PostgreSQL では NULL どうしは同じとみなされないので、何冊でも入る（要件どおり手入力は重複を判定しない）。
- 成功したら ID だけを返す。理由：本の詳細の画面は、追加の直後・再読み込み・本棚から開いたときのどれでも `GET /books/{本の ID}` で情報を取るため、ここで詳しく返しても結局もう一度取るため。作ったものの場所を `Location` ヘッダーで知らせる（HTTP の作法）。
- テスト：同時に2つ送っても1冊しか入らないこと、重複で 409 と本の ID が返ること、重複のときは Google Books を呼ばずに 409 になること。

#### 本棚に追加（手入力） `POST /api/v1/books`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `title`（必須・200文字まで）、`author`（任意・100文字まで）、`status`（`reading`／`finished`）。ほかの項目は 422 |
| サーバーですること | 入力を確かめて（前後の空白を除く・NFC に正規化・見た目の1文字で数える。5-1）保存する。`google_volume_id`・表紙の URL・ISBN は `NULL`。重複は判定しない |
| 成功 | 201、`Location: /api/v1/books/{本の ID}`、`{"id": "…"}` |
| エラー | 422 `VALIDATION_ERROR`（タイトルが空・長すぎるなど。画面の文は screens.md「2.」） |

- 著者が空のとき：項目がない・`null`・`""`・空白だけの4通りとも、空白を除いたあと空なら `NULL` として保存する。理由：`""` と `NULL` が混ざると「著者がいない本」を扱うたびに両方を気にする必要があるため、`NULL` の1つにそろえる（要件定義書の「空白だけの入力は未入力として扱う」のとおり）。Google Books に著者がない本も `NULL`。
- 手入力の本かどうかは `google_volume_id` が `NULL` かで判定する（要件定義書 5.2。手入力の本だけ後から編集できる）。

#### 本の詳細 `GET /api/v1/books/{book_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | パスの `book_id`（UUID） |
| 成功 | 200、下の形 |
| エラー | 404 `BOOK_NOT_FOUND`（自分の本でない・存在しない・削除済み）、422（`book_id` が UUID でない） |

```json
{
  "id": "3f2a…",
  "title": "嫌われる勇気",
  "author": "岸見一郎、古賀史健（なければ null）",
  "cover_url": "https://…（なければ null）",
  "status": "reading",
  "google_volume_id": "abc123（手入力の本は null）",
  "insight_count": 3
}
```


- 本の詳細の画面を開くたびに必要な情報（本の情報・読書ステータス・この本の気づきの件数）を1回でまとめて返す。理由：どれも本の詳細を開いたときに毎回必要で、呼ぶタイミングが同じため（`GET /me` と残り回数を分けたのは、呼ぶタイミングが違ったため）。気づきの件数はデータベースで数える（`COUNT`）。
- `google_volume_id` を返し、画面は「`null` なら手入力の本」として「本の情報を編集」を出す。理由：Google Books の本を編集する予定がなく、項目を増やさずに済むため。サーバーの編集の API でも同じ判断を必ず行い（画面を書き換えて送られることがあるため）、「Google Books の本の編集は断られる」をテストに入れて、画面とサーバーの判断の食い違いを防ぐ。将来2か所に書くのを避けたくなったら、サーバーが判断した `editable` を返す形に変える（項目を足すだけ）。
- 自分の本でない・存在しない・削除済みの場合は、どれも 404 `BOOK_NOT_FOUND`（他人の本があることを知らせないため）。`book_id` は UUID 型で受け取る（UUID でなければ 422）。

#### タイトル・著者の変更（手入力の本だけ） `PATCH /api/v1/books/{book_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `title`（200文字まで）、`author`（100文字まで。空なら `NULL`）。どちらか一方だけでもよい。ほかの項目は 422 |
| サーバーですること | 自分の本か確かめる（でなければ 404） → 手入力の本か確かめる（`google_volume_id` があれば 409） → 1つのトランザクションで、本のタイトル・著者と、その本の気づきに保存したタイトル・著者のコピーを書き換える |
| 成功 | 200、本の詳細（`GET /books/{book_id}`）と同じ形の変更後の本 |

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 入力の誤り（タイトルが空・長すぎるなど） | 422 | `VALIDATION_ERROR` |
| 自分の本でない・存在しない | 404 | `BOOK_NOT_FOUND` |
| Google Books から追加した本 | 409 | `BOOK_NOT_EDITABLE` |

- 読書ステータスの変更と API を分ける理由：読書ステータスはすべての本、タイトル・著者は手入力の本だけ、と対象が違うため。1つにまとめると、Google Books の本に読書ステータスとタイトルを一緒に送られたとき「一部だけ受け付けて一部断る」中途半端な場合の決まりが要るため。画面でも、読書ステータスは選ぶとすぐ保存、タイトル・著者はシートで直して保存、と操作が別のため。
- PATCH にする理由：すでにある1冊の一部（タイトル・著者）を変える操作のため。
- Google Books の本を 409 で断る理由：送られる値は入力として正しく（422 ではない）、断る理由は「Google Books の本である」という本の状態のため。422 は画面が入力欄の下に直し方を出す決まりで、今回は直すべき欄がないため。403 も意味は合うが、SHIORIME では 403 を使わない決まりにそろえる。画面は Google Books の本に「本の情報を編集」を出さないが、画面を書き換えて送られることがあるため、サーバーでも必ず確かめる（テストに入れる）。
- 本と気づきのコピーを1つのトランザクションで書き換える理由：途中で止まると、同じ本なのに気づきによってタイトルがばらばらになるため。全部成功したときだけ確定し（コミット）、途中で失敗したら全部取り消す（ロールバック）。

#### 読書ステータスの変更 `PUT /api/v1/books/{book_id}/status`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `status`（`reading`／`finished`） |
| サーバーですること | 自分の本か確かめる（でなければ 404） → 読書ステータスを書き換える |
| 成功 | 200、本の詳細（`GET /books/{book_id}`）と同じ形の変更後の本 |
| エラー | 422 `VALIDATION_ERROR`、404 `BOOK_NOT_FOUND` |

- URL：読書ステータスは「その本に付いている項目の1つ」なので、本の下に置く（`/books/{book_id}/status`）。すべての本が対象なので、作り方を表す `from-catalog` は使わない。URL に動詞は入れない。
- PUT にする理由：送った値で読書ステータスをまるごと置き換えるだけで、何度送っても同じ結果になる（冪等）ため。
- 変更が成功したとき（タイトル・著者の変更も）、変更後の本を本の詳細と同じ形で返す理由：変更は本の詳細の画面を開いたまま行い、同じ画面のまま表示を新しくするため。返ってきたもので置き換えれば、もう一度 GET しなくて済む（通信1回）。画面が自分で送った値をそのまま表示すると、サーバーが整えた値（前後の空白を除く・NFC）とずれることがあるため、サーバーが実際に保存した値を返す。本の追加（ID だけ返す）は、追加の後に別の画面へ移り、移った先で取るので事情が違う。

#### 本の削除 `DELETE /api/v1/books/{book_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | 自分の本か確かめる（でなければ 404） → 本を削除する（物理削除）。気づきは残り、気づきの `book_id` は `NULL` になる（ON DELETE SET NULL。気づきにコピーした本のタイトル・著者・表紙で「気づき一覧」に出る） |
| 成功 | 204 |
| エラー | 404 `BOOK_NOT_FOUND`（自分の本でない・存在しない・すでに削除済み） |

- すでに削除した本にもう一度 DELETE が来たら 404 を返す。理由：削除するとデータベースから行がなくなるので、サーバーからは「すでに削除した本」と「最初から存在しない本」の区別がつかないため。DELETE の冪等性は返事のステータスコードではなくデータの状態のことで、2回目に 404 を返しても「本がない」状態は変わらないので守られている。
- 画面は 404 を受けてもエラーとして見せず、本棚へ戻る（利用者がしたかった「本がない状態」にはすでになっているため）。204 なら本棚へ戻り、トースト「本棚から削除しました」。

### 7-4. 気づき一覧

#### 前提：「気づきのまとまり」と元の本の ID

- 気づき一覧の1件は「気づき」ではなく「本ごとの気づきのまとまり」。本棚にある本（気づき0件の本も含む）と、本棚から削除済みの本（気づきだけ残っている本）が混ざる。
- まとまりの ID は、元の本の ID（気づきの `original_book_id`）。本棚の本なら本の ID と同じ値。削除済みの本では books の行はないが、気づきに `original_book_id` が残っている（notes.md「気づき」）。
- まとまりを探す・まとめるのは、本棚の本でも削除済みの本でも、いつも `original_book_id` で行う（使い分けない）。気づきの `book_id` は「本棚にまだあるか」の判断（`NULL` なら削除済み）と、書くときに存在しない本を指せないようにする外部キーに使う。
- 題名・著者・表紙は、気づきが1つ以上あるまとまりは気づきの写し（本がある間は本の編集時に写しも更新するので、本の値と同じ）から取る。気づき0件の本棚の本だけは books から取る。
- まとまりが「ある」のは、自分の本棚にその ID の本がある（0件でもよい）か、自分の気づきにその `original_book_id` を持つものが1つ以上あるとき。

#### 気づき一覧 `GET /api/v1/insight-groups`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの（クエリパラメーター・どれも任意） | `sort`（`recent`／`many`／`few`。付けなければ `recent`）、`cursor`（続きの位置） |
| サーバーですること | 自分の気づきを `original_book_id` でまとめて件数・最後に書いた日時を数え（`GROUP BY`）、気づき0件の自分の本棚の本と合わせる → `sort` の並べ方で30件（＋続きがあるかを知るために1件多く）取る |
| 成功 | 200、下の形 |
| エラー | 422 `VALIDATION_ERROR`（`sort` が決まった値以外・`cursor` が壊れている・`cursor` の並び順と `sort` が違う） |

```json
{
  "items": [
    {
      "id": "3f2a…",
      "title": "嫌われる勇気",
      "cover_url": "https://…",
      "insight_count": 5,
      "last_written_at": "2026-10-25T03:12:00Z",
      "deleted": false
    }
  ],
  "next_cursor": "…（続きがなければ null）"
}
```

| 項目 | 中身 |
| --- | --- |
| `id` | 元の本の ID。本ごとの気づき一覧へ移るときに使う |
| `title`・`cover_url` | 題名・表紙の URL（表紙がなければ `null`） |
| `insight_count` | 気づきの件数（削除済みの本は必ず1以上） |
| `last_written_at` | 最後に気づきを書いた日時（ISO 8601・UTC）。0件なら `null`。「今日」「10月20日」への言い換えは画面側 |
| `deleted` | 本棚から削除済みなら `true` |

- URL を `/insights` にしない理由：`/insights` は「気づき1つ」を表し、`POST /insights`・`GET /insights/{id}` でもその意味で使う。一覧の1件は気づきではなく本ごとの集約なので、別の名前のリソースにする（集約リソース）。将来「すべての気づきを新しい順に」「気づきを言葉で探す」を足すときに `GET /insights` を空けておける。`/books` も、削除済みの本が入らないので使わない。
- 並び順はクエリパラメーター `sort` で受け取り、Python の `StrEnum` で3つに限る（FastAPI が3つ以外を自動で 422 にする）。画面の URL（`/notes?sort=few`）の値と同じにする。画面の URL に知らない値が書かれた場合は、画面側で最近書いた順として表示する。
- 並べ替えはサーバーでする（30件ずつ届くので、画面で並べると、まだ届いていない分が正しく並ばないため）。
- 並べ方（左から順に比べる）：

| `sort` | 並べ方 |
| --- | --- |
| `recent`（最近書いた順） | 最後に書いた日時（新しい順・0件の本は後ろ）→ 本棚に登録した日時（新しい順・削除済みの本は後ろ）→ 元の本の ID |
| `many`（気づきが多い順） | 件数（多い順）→ 最後に書いた日時（新しい順・ないものは後ろ）→ 本棚に登録した日時（新しい順・削除済みの本は後ろ）→ 元の本の ID |
| `few`（気づきが少ない順） | 件数（少ない順）→ 本棚に登録した日時（新しい順・削除済みの本は後ろ）→ 元の本の ID |

  - 削除済みの本は本棚に登録した日時がないので、同じ件数・同じ日時なら本棚にある本を先にする。削除済みの本のために日時の写しを持たせずに済む。
  - 最後に元の本の ID を付けて、並びを必ず1通りにする（タイブレーカー）。
  - 値がないものを後ろに置く（`NULLS LAST`）。カーソルで「この値より後ろ」を比べるときは、`NULL` を「とても古い日時」に置き換えてから比べる（`COALESCE`）。
- 続きの読み込みはカーソルにする。理由：気づき一覧は、気づきを書く・本を追加する・削除するたびに本の順番が動く。オフセット（何件目から）だと、読み込みの途中で40番目の本に気づきを書くと1番目に移り、ほかが1つずつずれて、さっき見た30番目の本がもう一度出る（削除では1冊飛ばされる）。カーソル（並びの値を目印にする。キーセットページネーション）なら、ほかの本はずれない。移動した本はこのスクロールの間は出ないが、一覧の一番上に移っているので開き直せば見える。
- カーソルには、最後に渡した1件の「並べ方の表の値すべて＋元の本の ID」と `sort` を入れ、Base64 で包む（中身を画面に意識させない）。例：`{"sort": "few", "count": 0, "registered_at": "2026-10-20T15:00:00Z", "id": "3f2a…"}`。カーソルの `sort` と URL の `sort` が違えば 422（目印の意味が合わないため）。
- 気づきの総数は返さない（画面に出さないため。screens.md「4. 気づき一覧」）。1件ずつに著者は入れない（一覧に出さないため）。

#### 気づきのまとまり1件 `GET /api/v1/insight-groups/{元の本の ID}`

本ごとの気づき一覧の画面の、上の部分（表紙・題名・著者・件数・削除済みか）に使う。

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | 自分の本棚にその ID の本があるか、自分の気づきにその `original_book_id` を持つものがあるかを確かめる（どちらもなければ 404） → まとまりの情報を返す |
| 成功 | 200、下の形 |
| エラー | 404 `INSIGHT_GROUP_NOT_FOUND`（他人の本の ID・存在しない ID・削除済みの本で気づきを全部消した） |

```json
{
  "id": "3f2a…",
  "title": "嫌われる勇気",
  "author": "岸見一郎、古賀史健",
  "cover_url": "https://…",
  "insight_count": 3,
  "last_written_at": "2026-10-25T03:12:00Z",
  "deleted": false
}
```

- 気づき一覧の1件と同じ形に `author`（なければ `null`）を足したもの。一覧は軽く、1件は詳しく。
- 画面は `deleted` が `true` なら「＋気づきを書く」を出さない。
- カードの API（下）に本の情報を一緒に入れない理由：カードは続きを読むたびに同じ API を呼ぶので、そのたびに使わない本の情報が届くため。続きのときだけ外すと、`cursor` の有無で返事の形が変わり、画面の処理が2通りになるため。URL と中身を合わせ（1つの URL が1つのものを返す）、一覧の返事を `{"items", "next_cursor"}` の形にそろえるため。画面を開くときは2つの API を同時に呼ぶので、待ち時間はほぼ1回分。
- 件数だけを返す API は作らない（この API の `insight_count` で足りる。細かく分けると呼ぶ回数が増える）。気づきを書いた・削除したあとは、この API をもう一度呼んで件数を取り直す。
- 画面は 404 を受けたら気づき一覧に戻る（本の詳細で 404 なら本棚に戻るのと同じ扱い）。削除済みの本で最後の気づきを削除したときも、まとまりがなくなるのでこれにあたる。

#### 本ごとの気づき一覧（カード） `GET /api/v1/insight-groups/{元の本の ID}/insights`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの（クエリパラメーター・任意） | `cursor`（続きの位置） |
| サーバーですること | 自分の気づきのうち `original_book_id` がその ID のものを、書いた日時が新しい順に20件（＋1件）取る → 20件分の次の一歩の数をまとめて1回で数える |
| 成功 | 200、下の形（まとまりがあって気づきが0件なら `items` は空） |
| エラー | 404 `INSIGHT_GROUP_NOT_FOUND`（上と同じ条件）、422 `VALIDATION_ERROR`（`cursor` が壊れている） |

```json
{
  "items": [
    {
      "id": "a1b2…",
      "page": 142,
      "quote": "他者の課題には踏み込まない",
      "body": "上司の機嫌を自分の責任だと思い込んで…（全文）",
      "next_step_count": 2,
      "created_at": "2026-10-25T03:12:00Z"
    }
  ],
  "next_cursor": "…（続きがなければ null）"
}
```

| 項目 | 中身 |
| --- | --- |
| `id` | 気づきの ID。気づきの詳細へ移るときに使う |
| `page` | ページ（1〜9999の整数。要件定義書の入力の上限）。なければ `null`（画面は「ページなし」） |
| `quote` | 引用。なければ `null`（画面は紙片を出さない） |
| `body` | 本文（全文） |
| `next_step_count` | 最新の完了したAI提案の行動プランの数（1〜3）。完了したAI提案がなければ 0（画面は出さない） |
| `created_at` | 書いた日時（ISO 8601・UTC） |

- URL を `/books/{本の ID}/insights` にしない理由：削除済みの本では `GET /books/{本の ID}` が 404 なのに、その下の `/insights` が 200 を返すと、親は「ない」のに子は「ある」ことになり意味が食い違うため（404 にすると、削除しても残すと決めた気づきが見られなくなる）。まとまり（`/insight-groups/{id}`）は削除済みの本でも存在するので、その下に置く（ネストしたリソース）。`/insights?book_id=…` は、`book_id` が削除で `NULL` になる列なので名前と中身がずれる。
- 本の詳細の「この本の気づきを見る」から来たときも、本の ID ＝ 元の本の ID なので同じ URL で開ける。
- 引用・本文は全文で返し、2行・3行に切るのは画面側（CSS の `line-clamp`）。理由：何文字で2行になるかは画面の幅や文字の種類で変わり、サーバーにはわからないため。本文は最大1000字なので、20件でも数十KB程度で済む。
- 次の一歩の数は、AI提案の数ではなく、最新の完了したAI提案の行動プランの数。最新のAI提案が作成中などで完了していなければ、その前の完了したAI提案の数を出す（完了以外は数えない。notes.md「AI提案」）。20件分を1件ずつ数えると問い合わせが20回になる（N＋1問題）ので、まとめて1回で数える（SQL の書き方は、行動プランの保存形式と一緒に database.md で決める）。
- カードに本の題名・著者は入れない（画面の上の部分を `GET /insight-groups/{id}` で取るため）。
- 並べ方は書いた日時が新しい順 → 気づきの ID。カーソルの中身は「書いた日時＋気づきの ID」（本棚の一覧と同じ作り）。

### 7-5. 気づき

#### 気づきを書く `POST /api/v1/insights`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `book_id`（必須。自分の本棚の本の ID）、`page`（任意。1〜9999の整数）、`quote`（任意。300文字まで。空なら `NULL`）、`body`（必須。1000文字まで。前後の空白を除いて空なら 422）。ほかの項目は 422 |
| サーバーですること | `book_id` で自分の本棚の本を探す（なければ 404） → 本から題名・著者・表紙の写しを作る → 気づきの `book_id` と `original_book_id` の両方にその本の ID を入れて保存する |
| 成功 | 201、`Location: /api/v1/insights/{id}`、本文 `{"id": "…"}` |

| エラー | ステータス | エラーコード |
| --- | --- | --- |
| 入力の誤り | 422 | `VALIDATION_ERROR` |
| 他人の本・存在しない本・本棚から削除済みの本 | 404 | `BOOK_NOT_FOUND` |

```json
{
  "book_id": "3f2a…",
  "page": 142,
  "quote": "他者の課題には踏み込まない",
  "body": "上司の機嫌を自分の責任だと思い込んで…"
}
```

- 題名・著者・表紙の写しは画面から受け取らず、サーバーが本から作る。理由：画面から受け取ると、書き換えられて本と違う題名の写しが保存されるため（本の追加で Google Books の情報を取り直すのと同じ考え方）。
- 送ってもらう本の ID は `original_book_id` ではなく `book_id`。理由：気づきを書けるのは本棚にある本だけで、名前で「本棚の本を指定する」と伝えるため。`original_book_id` はサーバーが保存時に自動で入れる列。
- 気づきに公開範囲は持たせない（要件定義書「公開範囲」）。
- 本棚から削除済みの本は、books に行がないので「存在しない本」と区別がつかず 404。気づきの `original_book_id` を調べれば削除済みとわかるが、画面は削除済みの本に「＋気づきを書く」を出さず、ここに来るのは画面を書き換えた送信だけなので、問い合わせを増やしてまで区別しない。
- 本を探してから保存するまでの間に、別の端末で本が削除された場合（TOCTOU）：気づきの `book_id` は books への外部キーなので、保存時にデータベースが拒否する（`IntegrityError`）。これを 404 `BOOK_NOT_FOUND` に読み替える。
- 画面は 404 を受けたら、移らずに上へ「この本は本棚から削除されたため、気づきを保存できませんでした。…」と出し、書いた内容を残し、「保存」を押せなくする（screens.md「7. 気づきの作成・編集」、見本 mockups/savedeleted.html）。
- 成功の返事を ID だけにする理由：保存のあと気づきの詳細へ移り、移った先が `GET /insights/{id}` で取り直すため（本の追加と同じ）。Location には画面の URL ではなく、そのものを GET できる API の URL を入れる。

#### 気づきの詳細 `GET /api/v1/insights/{insight_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | 自分の気づきか確かめる（でなければ 404） → 気づき・本の写し・最新の完了したAI提案・まだ終わっていないAI提案を返す |
| 成功 | 200、下の形 |
| エラー | 404 `INSIGHT_NOT_FOUND`（他人の気づき・存在しない・削除済み） |

```json
{
  "id": "a1b2…",
  "page": 142,
  "quote": "他者の課題には踏み込まない",
  "body": "上司の機嫌を自分の責任だと思い込んで…（全文）",
  "created_at": "2026-10-18T12:40:00Z",
  "book": {
    "id": "3f2a…",
    "title": "嫌われる勇気",
    "author": "岸見一郎、古賀史健",
    "cover_url": "https://…"
  },
  "latest_proposal": {
    "id": "p001…",
    "completed_at": "2026-10-20T09:30:00Z",
    "plans": [
      { "text": "次の会議で、結論から一言だけ発言する" },
      { "text": "発言したあとの気持ちを1行メモする" }
    ]
  },
  "pending_proposal": { "id": "p002…", "status": "processing" }
}
```

| 項目 | 中身 |
| --- | --- |
| `id`・`page`・`quote`・`body`・`created_at` | 気づきの中身。本ごとの気づき一覧のカードと同じ名前・型（`page`・`quote` はなければ `null`） |
| `book.id` | 元の本の ID（`original_book_id`）。戻るボタンで本ごとの気づき一覧（`/insight-groups/{id}`）へ移るときに使う |
| `book.title`・`book.author`・`book.cover_url` | 気づきに持たせた写し（著者・表紙はなければ `null`）。編集の画面の題名・著者にも使う |
| `latest_proposal` | 最新の完了したAI提案。`id`（「深掘りと回答も見る」で移る先）、`completed_at`（「10月20日のAI提案」）、`plans`（行動プラン1〜3個。AI の出力の形と同じ `{"text"}`）。まだ受けていなければ `null` |
| `pending_proposal` | まだ終わっていないAI提案。なければ `null`。`status` は `processing`（深掘りの作成中・行動プランの作成中。画面は「AI提案を処理中です」にし、`id` で2秒ごとに `GET /ai-proposals/{id}` を問い合わせる）か `failed`（状態が回答待ちで回答が入っているもの＝行動プランの作成に失敗。2-3 のとおり） |

- 本の情報を同じ返事に入れる理由：気づきの詳細は1件だけで続きの読み込みがないので、本ごとの気づき一覧のように同じ情報が何度も届く問題が起きないため。題名・著者・表紙の写しは気づきの表そのものに保存してある気づきの一部なので、URL と中身も合う。`book` にまとめるのは、本についての項目とひと目でわかり、画面の本の情報の部品にそのまま渡せるため。
- 本の情報は、本棚の本でも削除済みの本でも気づきの写しから取る（本がある間は本の編集で写しも更新されるので同じ結果）。削除済みかは、詳細・編集の画面の表示も操作も変わらないので返さない。本の ID（`book_id`）も、この画面から本の詳細へ移る道がないので返さない。
- AI提案を `latest_proposal` と `pending_proposal` の2つに分ける理由：「前の次の一歩を出しながら、新しいものを作成中」のように同時に起きるため。`pending_proposal` を1つにまとめ `status` を持たせるのは、作成中と失敗は同時に起きない（処理中なら新しく始められず、始めるときに失敗したものは削除する）ので、`is_processing`・`is_failed` に分けて「両方 true」というありえない組み合わせを作れないようにするため。
- 回答待ち（まだ回答していない）のAI提案は `pending_proposal` に含めない（`null`）。新しく始めると削除される決まりなので、ボタンは押せてよいため。
- データベースの4つの状態をそのまま返さず、画面に必要な形（処理中・失敗）に直して返す。データベースを変えても API の形を保てるようにするため。
- 本日の残り回数・アプリ全体の上限は、この API に入れず `GET /me/ai-usage` から取る。理由：気づきではなく自分（利用者）についての情報のため。確認のシートなど別の場面でも使い、AI提案を始めて断られたあとはこれだけ取り直せば済むため。画面を開くときは2つを同時に呼ぶ。`GET /me/ai-usage` は返す前に止まったAI提案を片付けるので、詳細を開いたときも正しい値になる。

#### 気づきの変更 `PATCH /api/v1/insights/{insight_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `quote`・`page`・`body`（どれも任意。下の表のとおり）。ほかの項目（`book_id` など）は 422 |
| サーバーですること | 自分の気づきか確かめる（でなければ 404） → 送られた項目だけ書き換える。本があるかは確かめない（本棚から削除した本の気づきも編集できる）。本の写し・AI提案には触れない |
| 成功 | 204 |
| エラー | 422 `VALIDATION_ERROR`、404 `INSIGHT_NOT_FOUND` |

| 項目 | 送らない | `null` | 空文字 `""` | 値 |
| --- | --- | --- | --- | --- |
| `quote` | 変えない | 消す | 消す（`NULL` として保存） | 300文字まで |
| `page` | 変えない | 消す | 422 | 1〜9999の整数 |
| `body` | 変えない | 422（必須なので消せない） | 422 | 1000文字まで |

- PATCH にする理由：すでにある1件の一部（引用・ページ・本文。本や書いた日時は変えない）を変える操作のため。編集の画面は3つを毎回そろえて送るので PUT でも成り立つが、PUT は本来そのもの全体を送る決まりで、気づきには送らない部分があるため。
- 「送らない＝変えない」「`null`＝消す」を区別する（部分更新。JSON Merge Patch と同じ考え方）。区別しないと、本文だけ直すと引用まで消える、または引用を消せない、のどちらかになるため。Pydantic の `model_dump(exclude_unset=True)` で、送られた項目（`null` を含む）だけを取り出す。
- 成功を 204 にする理由：保存のあと気づきの詳細へ移り、詳細は開くときにいつも `GET /insights/{id}` と `GET /me/ai-usage` で取り直すため。変更後のものを返すと、詳細の画面に「編集から来たときは受け取ったものを使う／それ以外は取る」の2通りの処理が要り、`pending_proposal` は編集の間にも変わりうるので結局取り直す必要があるため。本の変更（同じ画面のまま表示を新しくする）は 200 で変更後の本を返し、画面が移る操作は最小限を返す、という原則にそろえる。

#### 気づきの削除 `DELETE /api/v1/insights/{insight_id}`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | 自分の気づきか確かめる（でなければ 404） → 気づきを削除する（物理削除）。その気づきのAI提案もまとめて削除される（`ON DELETE CASCADE`） |
| 成功 | 204 |
| エラー | 404 `INSIGHT_NOT_FOUND`（他人の気づき・存在しない・すでに削除済み） |

- すでに削除した気づきへの DELETE は 404（本の削除と同じ。「すでに削除した」と「最初からない」は区別がつかず、2回目でも「気づきがない」状態は変わらないので冪等性は守られている）。画面は 404 を受けてもエラーを見せず、本ごとの気づき一覧へ戻る。戻った先のまとまりが消えていれば（削除済みの本の最後の気づき）、`GET /insight-groups/{id}` が 404 になり気づき一覧へ戻る。
- 行動プランの作成中でも削除は断らない（409 にしない）。理由：利用者が消したいものを AI の都合で消せないのは不便で、待つ理由もわかりにくいため。裏の処理は下のとおり安全に終われる。
- 行動プランの作成中に気づきを削除した場合、裏の処理（BackgroundTasks）が結果を保存しようとしても AI提案の行はもうない。保存は「この AI提案がまだ行動プランの作成中なら書き込む」という条件付きの1回の UPDATE にし、書き換えた行が0件なら結果を捨ててログに残して終わる（読み込んだ AI提案を書き換えて保存する書き方は、行が消えていると例外になったり行を作り直したりするため）。2分で止まったとみなして片付けたAI提案に遅れて結果が届いた場合も同じ書き方で守れる。

```python
result = db.execute(
    update(AiProposal)
    .where(AiProposal.id == proposal_id,
           AiProposal.status == ProposalStatus.GENERATING_PLANS)
    .values(status=ProposalStatus.COMPLETED, plans=plans, completed_at=now())
)
if result.rowcount == 0:
    logger.info("AI提案 %s は削除済みか状態が変わったため、結果を捨てます", proposal_id)
    return
db.commit()
```

- 削除しても、使ったAI提案の回数は戻さない。理由：OpenAI にはすでに頼んで費用がかかっているため。戻すと「始める → すぐ削除」を繰り返して回数を減らさずに AI を使えてしまうため。削除は利用者が選んだ操作で、通信の失敗（こちらの都合）とは違うため。

### 7-6. AI提案

処理の流れ（受け付けてすぐ返し、裏で AI を呼び、画面は2秒ごとに問い合わせる）は2章のとおり。ここでは各 API の形を決める。

#### 状態（`status`）

データベースの状態をそのまま返さず、画面の場面に合わせた7つの値に直して返す。

| `status` | 場面 | データベースでは | 回数 |
| --- | --- | --- | --- |
| `generating_question` | 深掘りの作成中 | 深掘りの作成中 | 使用済み |
| `awaiting_answer` | 回答待ち（まだ回答していない） | 回答待ち＋回答が空 | 使用済み |
| `generating_plans` | 行動プランの作成中 | 行動プランの作成中 | 使用済み |
| `plan_failed` | 行動プランの作成に失敗（送り直しできる） | 回答待ち＋回答あり | 使用済み |
| `completed` | 完了 | 完了 | 使用済み |
| `question_failed` | 深掘りの作成に失敗して終わった（2分で止まったとみなした場合も） | 深掘りの作成に失敗 | 失敗した瞬間に戻す（個人・アプリ全体） |
| `retry_limit_reached` | 送り直し3回でも失敗して終わった | 送り直しの上限 | 失敗した瞬間に本人の分を1回戻す |

- 「失敗」を画面に判断させず、サーバーが値に直して返す。理由：画面は `status` を見て出し分けるだけで済み、「回答待ちで回答があれば失敗」という決まりを画面が知らなくてよいため。`status` 1つで場面が決まるので、矛盾した組み合わせが生まれないため。データベースを変えても API の値は変わらないため。
- 深掘りの作成中と行動プランの作成中を1つにまとめない理由：出す文（「質問を考えています」「次の一歩を考えています」）も、一緒に出すもの（深掘り・回答があるか）も違うため。気づきの詳細の `pending_proposal` はボタンを押せなくするだけなので `processing` にまとめている（7-5）。
- 失敗して終わった2つの状態は、行をすぐには消さず、24時間の後片付けで消す（終端状態として残す）。理由：すぐ消すと、画面が問い合わせたときに 404 しか返せず、「深掘りの作成に失敗（回数を戻した）」「送り直しの上限（1回戻した）」「回答前に離れた・気づきごと削除（戻さない）」を区別できないため。画面が直前の状態から推測する方法は、たとえば深掘りの作成中に別のタブで気づきごと削除された場合に外れるため採らない。回数を戻すのは、行を消すときではなく失敗した瞬間（状態の変更と同じトランザクション）。
  - 残す期間を24時間にする理由：回答待ちの24時間の後片付けと条件をそろえ、片付けの仕組みを1つにするため。行は小さく数も少ない（1人1日3つまで）ので負担にならない。
  - 失敗して終わったものは、「同じ気づきで処理中なら新しく始められない」の処理中に数えない。新しく始めるときは、回答待ちのものと一緒に削除する。気づきの詳細の `pending_proposal` にも含めない（`null`）。利用者から見えるのは AI提案の画面の失敗の表示だけで、「完了したものだけが残る」は変わらない。
- 回答前に離れた・新しいAI提案で置き換えた・気づきごと削除・24時間の後片付けは、今までどおり行を消す。消えたAI提案は 404 になり、画面は「このAI提案は終了しました」と出す。

#### AI提案を始める `POST /api/v1/insights/{insight_id}/ai-proposals`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | 本文なし。`Idempotency-Key` ヘッダー（受付番号。UUID） |
| サーバーですること | 2-4 のとおり（自分の気づきか → 同じ受付番号のAI提案があればそれを返す → 処理中か → 回数 → 回答待ち・失敗して終わったものを削除 → AI提案を作って回数+1 → 裏で深掘りを作る） |
| 成功 | 202、`Location: /api/v1/ai-proposals/{id}`、本文 `{"id": "…"}` |
| エラー | 2-4 の表のとおり（429 `AI_DAILY_LIMIT`・429 `AI_APP_LIMIT`・409 `AI_PROPOSAL_IN_PROGRESS`・404 `INSIGHT_NOT_FOUND`） |

- 202 にする理由：返事の時点で AI提案の行は作ってあるが、中身（深掘り）はまだできておらず裏で作るため。201 は「作り終えた」なので、中身ができていないこの場面では 202 の方が正確。
- Location は、202 と一緒に使うときは「進み具合を確かめる場所」（画面が2秒ごとに問い合わせる URL）。
- 本文にも `id` を入れる理由：画面は画面の URL `/ai/{id}` へ移るのに ID を使う。Location の文字から切り出すと、画面がサーバーの URL の形（`/api/v1/…`）に頼ることになり、将来 URL を変えると壊れるため。本の追加・気づきの作成とも「Location＋`{"id"}`」でそろえる。
- 受付番号での送り直し（同じ番号が2回届いた）にも、1回目とまったく同じ返事（202＋同じ Location＋同じ `id`）を返す。画面は、どちらの返事かを区別せずに同じ画面へ移れる。

#### AI提案の取得 `GET /api/v1/ai-proposals/{proposal_id}`

AI提案の画面が、深掘りを待つ間・次の一歩を待つ間は2秒ごとに、見返しのときは1回だけ呼ぶ。

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| サーバーですること | 自分のAI提案か確かめる（でなければ 404） → 止まったものはその場で片付ける（2-8） → 今の状態と中身を返す |
| 成功 | 200（状態がどれでも 200。変わるのは中身） |
| エラー | 404 `AI_PROPOSAL_NOT_FOUND`（他人のもの・存在しない・削除済み） |

```json
{
  "id": "p002…",
  "status": "completed",
  "insight_id": "a1b2…",
  "insight": {
    "book_title": "嫌われる勇気",
    "page": 142,
    "quote": "他者の課題には踏み込まない",
    "body": "上司の機嫌を自分の責任だと思い込んで…"
  },
  "question": "黙ってしまう直前、頭の中ではどんな言葉が浮かんでいますか？",
  "answer": "無能だと思われたくない、という焦りだと思う。…",
  "plans": [
    { "text": "次の会議で、結論から一言だけ発言する" },
    { "text": "発言したあとの気持ちを1行メモする" }
  ],
  "completed_at": "2026-10-20T09:30:00Z",
  "retries_left": 3
}
```

| 項目 | 中身 | `generating_question` | `awaiting_answer` | `generating_plans` | `plan_failed` | `completed` | 失敗して終わった2つ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `id`・`status` | AI提案の ID・状態 | ○ | ○ | ○ | ○ | ○ | ○ |
| `insight_id` | 元の気づきの ID（「気づきに戻る」） | ○ | ○ | ○ | ○ | ○ | ○ |
| `insight` | あなたの気づき | ○ | ○ | ○ | ○ | ○ | ○ |
| `question` | AIからの深掘り | null | ○ | ○ | ○ | ○ | `question_failed` は null |
| `answer` | 回答（`plan_failed` では入力欄に戻す） | null | null | ○ | ○ | ○ | `retry_limit_reached` は ○ |
| `plans` | 次の一歩（1〜3個。`{"text"}`） | null | null | null | null | ○ | null |
| `completed_at` | 完了した日時（「10月20日のAI提案」） | null | null | null | null | ○ | null |
| `retries_left` | 送り直せる残りの回数 | 3 | 3 | 数 | 数 | 数 | 数 |

- どの状態でも同じ項目を返し、まだないものは `null` にする。理由：画面は「この項目があるか」を状態ごとに覚えず、`null` なら出さない、とだけ書けばよいため（7-5 の `latest_proposal` と同じ考え方）。
- `insight` の引用・本文は、AI提案を始めた時点の写し（notes.md「AI提案」）。その後に気づきを編集しても、AI提案は始めた時点の内容に対するものなので写しを返す。本の題名とページは AI提案に写していないので、元の気づきから取る。
- `retries_left` は、サーバーが「3 − 送り直した回数」を計算して返す。送り直した回数はサーバーで数える決まりで、上限が変わっても画面を直さずに済むため。
- 完了した直後の画面と見返しの画面（「あなたの気づき」から全部出す・「気づきに戻る」を出さない）は、同じ返事から作り、画面がどこから来たかで出し方を変える。

#### 回答を送る `POST /api/v1/ai-proposals/{proposal_id}/answer`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `answer`（必須。1〜500文字。前後の空白を除き、見た目の1文字を1文字として数え、NFC にそろえる）。ほかの項目は 422 |
| サーバーですること | 自分のAI提案か確かめる（でなければ 404）→ 回答待ちのまま24時間を過ぎていればその場で消して 404（2-8）→ 1回の条件付き UPDATE で「状態が回答待ち（回答が空）なら、回答を保存して行動プランの作成中にする」→ 書き換えた行があれば裏で AI を呼ぶ |
| 成功 | 202（Location・本文なし） |
| エラー | 422 `VALIDATION_ERROR`、404 `AI_PROPOSAL_NOT_FOUND`、409 `AI_PROPOSAL_STATE_CONFLICT`（下の「状態が合わない操作」） |

- 名前は取得の返事の `answer` とそろえる。
- 202 の理由：次の一歩はまだできておらず、裏で作り始めたところのため。画面は 202 を受けたら自分で作成中の表示に切り替え、2秒ごとの問い合わせを始める。
- Location を付けない理由：始める API で付けたのは、新しく作ったAI提案の問い合わせ先を初めて知らせるためで、回答の送信では問い合わせ先は今いるAI提案そのもので画面がもう知っているため。本文も、ID・問い合わせ先とも画面が知っており、最新の中身は問い合わせの GET で取るため返さない（返事の中身を1か所にまとめる）。

#### 送り直す `POST /api/v1/ai-proposals/{proposal_id}/retry`

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | `answer`（必須。1〜500文字。直していてもいなくても、入力欄の回答をそのまま送る） |
| サーバーですること | 自分のAI提案か確かめる（でなければ 404）→ 1回の条件付き UPDATE で「状態が `plan_failed` で、送り直した回数が3未満なら、回数+1・回答を上書き・行動プランの作成中にする」→ 書き換えた行があれば裏で AI を呼ぶ。1日の回数は使わない |
| 成功 | 202（Location・本文なし。`/answer` と同じ） |
| エラー | 422 `VALIDATION_ERROR`、404 `AI_PROPOSAL_NOT_FOUND`、409 `AI_PROPOSAL_STATE_CONFLICT` |

- `/answer` と分ける理由：受け付けてよい状態（`awaiting_answer` と `plan_failed`）が違い、送り直しだけが「送り直した回数を+1して上限を確かめる」をするため。1つの API の中で状態によって回数を数えたり数えなかったりするより、API ごとに役割を分けた方が、数え忘れ・二重に数えるの間違いが起きにくいため（単一責任）。画面は問い合わせで状態を知っており、ボタンの文も別なので、どちらを呼ぶか選ぶのは簡単。URL で送り直しが見分けられ、ログ・テストもしやすい。
- `answer` を必須にする理由：「省略したら前の回答を使う」と「送られたら上書き」の2通りにすると分かれ道が増えるため。画面は入力欄に回答を持っているので、いつも送ってもらえば1通りで済む。
- 1回の条件付き UPDATE にする理由：ボタンを素早く2回押したり、2つのタブから同時に押したりしても、条件に合うのは1回目だけなので、回数が二重に増えたり AI を二重に呼んだりしないため。
- 最初の送信＋送り直し3回の4回目の失敗で `retry_limit_reached` になるので、`plan_failed` のときは必ず残りが1回以上ある。

#### 途中でやめる `POST /api/v1/ai-proposals/{proposal_id}/abandon`

AI提案の画面を開き直した（再読み込み・戻る/進む・URL の直接入力）とき、状態が回答を送る前なら、画面は「このAI提案は終了しました」と出し、この API でサーバーに終了を伝える（要件定義書 5.5、notes.md「AI提案」）。

| 項目 | 内容 |
| --- | --- |
| 認証 | 必要 |
| 受け取るもの | なし |
| サーバーですること | 自分のAI提案か確かめる（でなければ 404）→ 1回の条件付き DELETE で「状態が `generating_question`・`awaiting_answer`・`plan_failed` なら削除する」。回数は戻さない |
| 成功 | 204 |
| エラー | 404 `AI_PROPOSAL_NOT_FOUND`、409 `AI_PROPOSAL_STATE_CONFLICT` |

- DELETE にしない理由：`DELETE /ai-proposals/{id}` は「どの状態でも消せる」と読めるが、消してよいのは回答を送る前だけで、完了したもの・行動プランの作成中のものは消さないため。この API の意味は「利用者が途中でやめたので、決まりに従って終わらせる」という手続きで、削除はその結果にすぎない。将来「完了したAI提案を消す」を作るときのために `DELETE` を空けておける。
- POST にする理由：POST は登録だけでなく「その URL の決まりに従って手続きを処理させる」メソッドで、GET・PUT・PATCH・DELETE のどれにも当てはまらない操作に使う。ログイン・退会・回答の送信と同じく、条件を確かめて状態を進める手続きなので、URL の最後に操作の名前を付ける例外にする（カスタムメソッド）。PATCH で状態の値を書き換える形は、画面が `completed` などに書き換える不正も考える必要が出るため採らない。
- 1回の条件付き DELETE にする理由：終わらせる瞬間にちょうど状態が進んだ（深掘りができた・回答が届いた）場合に、間違って進んだものを消さないため。
- 深掘りの作成中に終わらせた場合、裏で AI が質問を作り終えても、保存は条件付き UPDATE なので行がなければ捨てて終わる（7-5 の気づきの削除と同じ）。
- 404 が返った場合（もう消えていた）、画面はもともと「終了しました」を出すつもりなので、エラーとして見せずにそのまま出す。

#### 状態が合わない操作

| 場面の例 | 返事 |
| --- | --- |
| 回答のボタンを素早く2回押した（2回目は状態がもう `generating_plans`） | 409 `AI_PROPOSAL_STATE_CONFLICT` |
| 2つのタブで同じAI提案を開き、片方で回答済み。もう片方からも回答した | 409 `AI_PROPOSAL_STATE_CONFLICT` |
| 「もう一度送る」を押したが、別のタブでもう送り直していた | 409 `AI_PROPOSAL_STATE_CONFLICT` |
| 開き直して `/abandon` を送ったが、その一瞬前に回答が届いて作成が始まっていた | 409 `AI_PROPOSAL_STATE_CONFLICT` |
| 回答を書いている間に、別のタブで終了させた・気づきごと削除・24時間の後片付け | 404 `AI_PROPOSAL_NOT_FOUND` |

```json
{"error": {"code": "AI_PROPOSAL_STATE_CONFLICT", "message": "AI提案の状態が変わっています。最新の状態を表示します。"}}
```

- AI提案はあるが状態が合わない → 409。エラーコードは1つにまとめる。理由：原因はどれも「別の操作（2回目の押し・別のタブ）が先に状態を進めていた」で、画面の動きも同じ（`GET /ai-proposals/{id}` で取り直し、今の状態の表示に切り替え、必要なら問い合わせを始める）ため。場面ごとに分けても画面の動きは変わらない。
- 409 はエラーとして見せない（利用者は何も間違えていないため）。黙って最新の表示に切り替える。
- AI提案がない → 404。画面は「このAI提案は終了しました。気づきの詳細から新しく始めてください」と「気づきに戻る」（要件定義書 5.5）。
- サーバーは、条件付きの UPDATE・DELETE で書き換えた行が0件なら、行があるかをもう一度確かめ、あれば 409、なければ 404 を返す。
- テスト：上の表の場面をそれぞれテストにし、同時に押されたときに回数・送り直しの回数が二重に増えないこと、AI を二重に呼ばないことを確かめる。
